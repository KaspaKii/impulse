# Impulse browser demo (phases 1 and 2)

A static page for Impulse, the atomic delivery-versus-payment primitive for Kaspa: plain, dark, minimal, no framework, no analytics, no third-party script. Use only values you can afford to lose. Not deployed.

Phase 1 (increment I11) is the part that needs no keys and no node: a terms form, the terms hash and both vault addresses derived as you type, funding instructions with the `kaspa:` funding URI of each native KAS leg as text and as a QR code, a per-trade value cap and mainnet behind an explicit switch. Phase 2 adds what needs a key and a node: the role check, two wallets made in the page, a node client, the settle, the Direct trade and the refund (built from the node's UTXOs, reviewed, signed in the page, submitted), and the decoder wired to the node. The page funds one thing, the buyer's KAS cash leg, from a wallet of the page; a KCC-20 leg is funded with the command line, and a transaction that needs a key the page does not hold is exported as text, signed with the command line, and its signatures are added back (integration follow-up of 2026-10-11).

## Build and run

```
crates/impulse-wasm/ci.sh        builds the SDK (wasm-pack) into crates/impulse-wasm/npm/pkg
demo/build.sh                    copies the pages and the SDK into demo/dist and writes the examples from the golden terms vectors (pin-examples.mjs)
cd demo/dist && python3 -m http.server 8000
```

Open `http://localhost:8000/`. The SDK is bundled in `dist/sdk/`; the page loads nothing from anywhere else. Serve `.wasm` as `application/wasm`.

`demo/ci.sh` builds, type-checks and runs the browser tests in headless Chrome or Chromium (`IMPULSE_BROWSER` names the binary if it is not at a usual path), and checks that `mutation-run.txt` names the sources as they are (`node demo/mutation.mjs --verify-record`). It is a step of `scripts/ci-local.sh`. The mutation run itself (`node demo/mutation.mjs --record`) is by hand: it takes as long as the suite times the number of mutants.

## What the page does

- **Terms form.** One field per key of the JSON form of terms (`spec/ENCODING.md`). Load an example from the list, paste terms text, or type. The examples are the golden vectors with the token of each KCC-20 leg replaced by the first pinned kcc20.sil build (`pin-examples.mjs`, run by `build.sh`; the file says so in its description), because the vectors as committed name a synthetic token that is no kcc20.sil build, and no funding is ever given for such a token: the page refuses the vectors as committed (`SDK_TEMPLATE_UNPINNED`), as `impulse address` refuses them. Pasted and fetched text goes to the SDK as text (`Terms.fromFileText`): it must be the JSON form of terms, a terms file (`terms`, `canonical`, `terms_hash`) or a golden vector file, name no key twice, hold a u64 only as a decimal string, and, for the two file shapes, carry a `canonical` and a `terms_hash` that are those of its `terms` (`SDK_TERMS_INCONSISTENT`). Nothing is filled into the form before the SDK has accepted the text, and the SDK compares what the form then holds with what it read. Party keys are public keys you type, or the public keys of the page's wallets (the wallet cards fill them in). Loading terms clears the KAS declaration, so every trade needs a fresh one.
- **The four destinations.** Before the legs, open by default: `buyer_delivery`, `seller_proceeds`, `seller_refund` and `buyer_refund`, decoded by the SDK as Kaspa addresses or KCC-20 owners and marked `pays seller_key`, `pays buyer_key`, `pays authority_key` or `script to check`. A destination that pays the key of the party that does not own it, or the authority's, is shown with a warning, because the contract lets those parties trigger a refund. The page does not know which party you are, so this is a mark, not the role check.
- **Every leg.** Each vault says who funds it and that anyone else sends nothing to it. Every KCC-20 leg carries `TOKEN_UNASSESSED`: the page reads no token artifact, so nothing about the token's issuer powers was read.
- **Live derivation.** Every edit goes to the SDK, which is impulse-core compiled to WebAssembly. The SDK checks the terms, the creation checks, the value cap and every escrowed leg, and returns the terms hash, the template hash, the vault addresses and the funding URIs. The page only shows what the SDK returns, and shows nothing at all when the SDK refuses, with the stable refusal code (`TERMS_*`, `TEMPLATE_*`, `SDK_*`).
- **Funding instructions.** For a native KAS leg: `<vault address>?amount=<sompi>&impulse=<terms hash>` as text and as a QR code (drawn on the page from the SDK's QR matrix). A KCC-20 leg gets its vault address and the escrowed token owner (SCRIPT_HASH) and no URI, because it is funded with two outputs. A leg the terms do not escrow (Direct mode, external cash) is shown as having no vault.
- **Value cap.** 10 KAS per trade (decision D4, default, the same as the command line and the SDK), set in `config.js`. The page refuses a trade whose declared KAS value, or whose native KAS leg, is above the cap. Every v1 trade has a KCC-20 asset leg whose value the page cannot know, so the value is the figure you declare in sompi and nothing checks it. The SDK refuses a cap above its default, so the page can only lower it, and it has no way to lift it. A trade above the cap, or without a declaration, is refused and nothing is shown.
- **Creation DAA score.** Typed, or read from the node you connected to (a button). A typed score is marked as typed; a score read from the node counts as read only while the field still holds exactly what the node gave. The page shows the approximate time left to expiry from that score, so a stale one is visible.
- **Mainnet.** Off by default. The switch shows the mainnet notice, sets the network of the creation checks (terms of the other network are refused, `TERMS_NETWORK_MISMATCH`), closes any node connection, open or still opening (a socket that opens after the switch is closed and never used), and forgets a score read from it. The node client also refuses, unsent, any request on a connection checked for the other network than the page's. On mainnet the SDK refuses a creation DAA score that was typed (`SDK_MAINNET_NEEDS_NODE`, the rule of `spec/CLI.md`), so mainnet works only with a node: `wss://`, or `ws://` to `localhost` or `127.0.0.1`. The role check exists in Rust, which is the condition of the phase 1 review for enabling this.
- **You.** Before the page shows anything to fund or offers any action, it asks which party you are (buyer or seller), your public key and, if a destination is a custodian's, the pin for it. The SDK's role check refuses terms whose destinations for your role pay the counterparty or the authority (whatever you pin), or pay a script you did not pin. The page shows a funding URI and a QR code only for the leg your role funds.
- **Node.** One WebSocket to the wRPC JSON address you type (a kaspad started with `--rpclisten-json`). The SDK checks the URL (`ws://` or `wss://`; on mainnet `wss://` or `ws://` to `localhost` or `127.0.0.1`; `ws://[::1]` is refused with `SDK_NODE_INSECURE`) before a socket is opened, and the node once it answers (the network the page acts on, synced). There is no default node. The page asks it for its state, for the UTXOs of the addresses the SDK names, and, on your click, sends it the signed transaction. Requests go one at a time, and a reply is read by the SDK as text.
- **Wallets.** Two, A and B. A key is drawn by the SDK's `Wallet` from the browser's randomness, held in the SDK module's memory and never given to the page's code: the page sees a public key and signatures. The page's code never stores, shows, sends or logs a key and has no control that exports one; the browser and the engine may keep copies of the bytes they handled, which the page cannot clear. It is wiped by the Wipe button, by "Wipe both wallets", and when the page is hidden or unloaded (`pagehide`); a wiped wallet signs nothing. Wipe asks first when the last balance read from the node was above zero, or when the wallet funded a cash vault and the page has not seen that trade settled or refunded. The page asks the browser to confirm a navigation away (`beforeunload`) while a wallet holds a key, and wipes nothing on that event, because a navigation that is then cancelled leaves the page up. **A wallet is a signing key and a source of fee inputs, not a place to keep KAS:** the page has no button that sends KAS from a wallet to an address you type (the only transactions it builds are the trade's own: the funding of the cash leg, the settle, the Direct trade, the refund), so whatever a trade pays to a wallet's key (the delivered token, the proceeds, a refund, the change, the vault's authorizer coming back to a seller's key) can be spent from the page only as an input of another transaction it builds, and is lost with the page. On mainnet the SDK therefore refuses any destination of your role, any change and any other output that pays a key of these wallets (`SDK_DESTINATION_IN_WALLET`); on testnet it is allowed and the role check and the review say so. The remedy is a pin for each destination of your role and a change address, all of them addresses you control elsewhere. When the page holds both parties' keys (a Direct trade between wallet A and wallet B on mainnet), each wallet signs under its own party's pins: yours in the pin fields, the other party's in the fields for the other party, and no wallet gets the other's.
- **Settle, Direct and refund.** For Vault terms: "Build the settle" and a refund of a leg by the depositor, the counterparty or the authority, with or without the escrowed token. For Direct terms: "Build the Direct trade". The SDK names the addresses to ask about, chooses the UTXOs from the node's answer by fixed rules (largest plain UTXO at a vault, exact token state, exact KAS amount; the fee payer's own UTXOs, never one a leg uses) and calls the builder. The page then shows the review: every input and output with its amount, address and what the terms say it is, the fee, the minimum relay fee, the masses, the lock time and when the node will take it. The review also names the terms hash and nonce of the trade, the cost beyond the fee that the fee wallet pays (a counterparty who funds a vault's authorizer below the minimum makes it pay the difference), whose key each signature is for, a note for the authority's signature (for external cash: the cash is paid outside Kaspa and the signature attests it), and which outputs pay a key held only in the page. Each wallet that holds a key some input needs gets a button; signing is `Wallet.sign`, which checks the document against its terms, the value cap and the role, and then the payer's side: the change pays the address you gave (empty, the wallet's own key), the fee is at most twice the minimum relay fee, the top-up of under-funded outputs is none, and what the wallet commits is what the trade takes from it. Two fields raise the fee and top-up limits for a document you have read. A change address you give is also what the builder pays the change to. Submit asks the node for its score again, refuses (sending nothing) if the lock time has not passed or the expiry has, and sends the one signed transaction. If the request left the page and the answer did not come back (no answer in 20 s, a closed connection), the outcome is unknown, not refused: the page gives the transaction ID, a link to the decoder in another tab and a button that asks the node's mempool, and keeps submit off until it has been asked. A build still in flight when the terms, the role or the node change is thrown away. A transaction needing a key the page does not hold is handed over as a partially signed transaction (IPST) text.
- **Funding the cash leg.** For a Vault trade with a native KAS cash leg, to the buyer: "Build the funding of the cash leg" (`fundCashAddresses`, `fundCashFromReply`). The page asks the node for the UTXOs of the cash vault, the asset vault, the token escrowed in the asset vault and the fee-payer wallet, and the SDK builds one output of exactly the cash amount at the cash vault, paid by the chosen fee-payer wallet's own plain UTXOs (largest first, enough for the deposit and the fee, change zero or at least the minimum output) with the change at the change address; the wallet must hold the buyer's key (`SDK_FUND_NOT_YOUR_LEG` otherwise). It builds only at the node's score now (the creation checks run with it: nothing is built at or after the expiry), and only when the node lists the seller's asset leg (the authorizer at the asset vault and the token in its exact state: `SDK_FUND_ASSET_NOT_FUNDED` otherwise) and no deposit of exactly the cash amount at the cash vault yet (`SDK_FUND_ALREADY_FUNDED`), because the buyer's only way to take the deposit back unaided is a refund signed by this wallet's key, from the expiry in earmarked mode. A KCC-20 token whose template is not a pinned kcc20.sil build is never funded (`SDK_TEMPLATE_UNPINNED`, no override, as for `impulse address` and `fund build`). The review is the same, with the deposit named as the cost beyond the fee and a first note that says how the deposit comes back and that closing the page or wiping the wallet destroys that way out; the wallet signs through `Wallet.sign`, which checks the funding like any other document (the deposit and the fee are what it commits, the value cap counts both, the key is the leg's depositor, the terms are fundable at the node's score, and on mainnet a change to a key of the page is refused). The page remembers the deposit from the moment it writes the funding to the node, whatever it hears afterwards: the wallet's card says it funded a cash vault, and Wipe and "Wipe both wallets" ask first, naming each deposit, until the page itself submits the settle or a refund of the cash leg of that trade (one settle ends one deposit; a trade settled by someone else is not seen, so the page may ask when it need not; it does not fail to ask when it should). A wallet keeps one entry for each funding, so funding a second trade from the same wallet adds to the first. Only the node's own error to the request (a well-formed reply with the request's id and an `error`, which the SDK marks `nodeError`) clears the entry. A reply the page cannot read or match to its request, a hang-up or no answer is an unknown outcome and counts as a deposit: the page gives the transaction ID and a link to the decoder, and keeps submit off, even if the terms were edited meanwhile. The review of a funding also says how long the trade has left to settle: a settle is refused at or after the expiry. The button is not offered to the seller, for Direct terms, external cash or a KCC-20 cash leg; the SDK refuses those askers too. The seller funds the asset leg with the command line, the node is expected to list the deposit once a block accepts it (from the node's source; not yet observed against a real node), and the settle is then built as before. The page's automatic fee is the minimum relay fee and a tenth more; the command line's is the minimum itself, so type the same fee on both sides to get the same transaction.
- **Export and import of the partially signed transaction.** A document that needs a key the page does not hold (the seller's token in a Direct trade) is shown with the signatures it has, and "Copy" puts its text on the clipboard. `impulse ipst sign` signs it outside the page, and "Add its signatures" takes the signed text: the SDK's `combine` adds only the signatures the document under review lacks, only from a document that is exactly this one (same terms, inputs, outputs and slots: `IPST_CONFLICT`), and verifies each against its input (`TX_SIGNATURE`). The result is reviewed again, with the terms check, at the node's DAA score as the page reads it then (hours may have passed since the build: a lock time that has passed reads as final, and an expiry that has passed refuses the import, `TX_EXPIRED`, with the screen as it was), before submit is offered; if the node cannot be asked, the signatures are still added and the status says the review keeps the score of the build. A pasted document never replaces the one reviewed, and with no document under review the import is refused. If the browser refuses the copy, the page opens the block with the text and says so, so that it can be selected and copied by hand. Nothing but the final signed transaction is sent anywhere.
- **Decoder page.** Fetches a transaction by its ID from the node you type: the node's mempool first, then, if you give a chain block to start from (the trade page prints it after a submission), along the chain. A node keeps no index of transactions by ID, so the block is needed for an accepted transaction. The SDK checks that what the node returned hashes to the ID asked for, finds the vault inputs, and reads their terms back from the scripts they reveal. The page shows each leg (the entry used, what was delivered or refunded and to whom, the terms hash and the terms), the template-hash check (and whether the decoding is bound to the scripts the inputs spend, which a mempool entry never is), and what the node says about the acceptance (the chain block, its DAA score, and how many DAA scores the node is past it, which is a distance, not a count of confirmations). It follows the chain page by page, up to 200 pages, and says when it gave up before the node's tip; a block that left the chain no longer counts as accepting. It is not a signed receipt.

## Not in this build

The funding of a KCC-20 leg (it needs a covenant transfer that no ordinary wallet makes: use the command line's `fund build`), any funding, settle or refund of terms whose KCC-20 token is no pinned kcc20.sil build (the page derives nothing for such terms, so it offers no action on them; the command line's `refund build` and `settle build` do not check the pin, and remain the way to take such a trade apart), and Netlify deployment with response headers. Nothing is deployed or published from this directory. Whether a real node accepts what the page builds has not been checked: the wire forms are written from the node software's source and tested against an offline stand-in.

## Safety notes the page repeats

- The role check ran for the role and key you gave. It does not say who controls a script you pinned, and it does not read the token (every KCC-20 leg carries `TOKEN_UNASSESSED`). Read the four destinations.
- The URI states the amount in sompi. Whether wallets read it as sompi is not yet checked against real wallets: confirm the wallet shows the KAS and sompi amount given on the page.
- The wallets are in memory only. There is no backup and no export, and a wallet is not a place to keep KAS.
- The fee rule, the lock-time rule and the mempool's handling of the transaction (it sets the storage mass field itself) are written from the node software's source and have not been run against a node.

## Disclaimer

Impulse is non-custodial software: it holds no funds and no keys, and signing happens only on the key holder's machine. Nothing in it, or in this documentation, is financial, legal or tax advice, or an offer or solicitation to buy or sell anything. Impulse issues no asset and no token: any asset or token a trade moves is issued by someone else. ## Policy

Both pages are served with a Content-Security-Policy (a `<meta>` tag) that allows scripts from their own origin and WebAssembly compilation, no `eval`, and connections to their own origin, to any host over `wss:` and over `ws:` to `localhost` and `127.0.0.1` only (a host-source cannot name an IPv6 literal, so `[::1]` is not allowed; the SDK refuses it on mainnet before a socket is opened). The node is the URL the user types, so the policy cannot name it: a script of the page's own origin could open a `wss:` socket to any host. The defence is that the page has no third-party script, no inline script and no markup built from text (all checked by `demo/test/page.test.ts`), that the page's code opens a socket in one place (`node.js`) to the typed URL, and that the browser tests record every socket the page opens. `demo/test/` checks in a real browser that the policy holds, that the page requests nothing from another origin, that it uses no storage, cookie or WebCrypto key call, that it fetches only its own files and the golden vectors, and that, through a whole trade, no wallet key appears in the DOM, the storage, the network traffic, the console or the page's globals (with the scan shown to find a key planted in each).

The only text from outside the page that reaches the document is set as text, never as markup.

## Tests

`demo/test/*.test.ts` run in headless Chrome or Chromium against `demo/dist`. The node is an offline stand-in (`crates/impulse-wasm/npm/test/fakenode.ts`) reached through Playwright's WebSocket routing; its header says what it checks (that every input spends an unspent UTXO it holds, that the inputs hold at least what the outputs pay, that the lock time is below its score, that a signature script is present) and what it does not (no script is run, no signature is verified, no mass is computed). `session.ts` holds the steps of a person; `world.ts` the trades (a mainnet trade pays an address elsewhere, `coldTermsFor`); `party.ts` an address encoder written for the tests, so that the expectation does not come from the SDK. The tests use a node URL on port 1, not kaspad's default port, so that an interception that failed open would reach a closed port. `paths.test.ts` runs the two trades of the exit test as the owner runbook does (a Vault trade whose cash leg the buyer funds from the page, and a Direct trade whose token input is signed outside the page and added back), with the key holder played by a runtime throwaway key of the SDK that is never written anywhere; `chain.test.ts` runs the decoder against a node that pages its answers and reorganises its chain; `node.test.ts` and `component.test.ts` run the page's node client and review renderer on their own, in a real browser, with stand-ins for the socket and the SDK where a trade cannot reach the case. The wallet test reads the keys through an independent implementation (`@noble/curves`, a dev dependency of the SDK package, imported only by the tests).
