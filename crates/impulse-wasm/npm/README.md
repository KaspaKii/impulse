# @warpcore/impulse (name pending)

The Impulse SDK for TypeScript and JavaScript: trade terms, ImpulseVault redeem scripts and funding addresses for Kaspa, compiled to WebAssembly from `impulse-core`.

Status: not published (`"private": true` until the release increment). Use only values you can lose.

Every operation is implemented once, in Rust: the terms, template, address, transaction, IPST, verify and decode operations are `impulse-core`'s, and the argument checks, the JSON forms and the value cap are in `crates/impulse-wasm`. The JavaScript in this package only re-exports the generated bindings. The golden vectors in `tests/vectors/` are checked through the SDK by the TypeScript suite: the terms and vault vectors are reproduced byte for byte (JSON form, canonical bytes, terms hash, redeem scripts, script hashes, scriptPubKeys, addresses); each of the 13 IPST vectors is read, written back to the exact text of its file, and rebuilt from its own inputs by the builders called from TypeScript (`fundKas`, `fundKcc20`, `settle`, `refund`, `direct`), and the rebuilt text must equal the file.

Keys: the transaction, IPST, verify and decode operations are keyless: a signature reaches them as 65 bytes that a caller made elsewhere, and is verified before it is stored. One class holds a key, `Wallet` (added for the browser demo, I11 phase 2, below): a key the module draws once from the browser's randomness, keeps in its own memory and never hands out. Nothing else in the package signs or draws randomness, and CI counts the draws.

## Scope (increment I9)

Phase 1: terms, the template and addresses. Phase 2: the transaction builders, sighash, signature verification, assembly, the IPST, and the verifier and decoder. For the browser demo (I11): the funding instructions and the role check, the in-page `Wallet`, the review a signer reads, the node's wRPC JSON forms and the builders that work from a node's UTXOs. Not in this package: a socket. The page opens the WebSocket to the node and hands the text of each reply to the SDK.

## Loading

The module is an ES module built with `wasm-pack --target web`. Initialise it once before any call.

Browser, served next to `pkg/impulse_wasm_bg.wasm`:

```js
import init, { Terms } from "@warpcore/impulse";
await init();
```

Node:

```js
import { readFileSync } from "node:fs";
import { initSync, Terms } from "@warpcore/impulse";
initSync({ module: readFileSync(new URL(import.meta.resolve("@warpcore/impulse/impulse_wasm_bg.wasm"))) });
```

Import the package entry only. The generated module in `pkg/` also carries the wasm-bindgen exports of the rusty-kaspa crates linked into it, among them `initBrowserPanicHook` and `presentPanicHookLogs`, which write panic logs into the page through `innerHTML`. The entry does not export them, and nothing in the SDK calls them. `crates/impulse-wasm/wasm-imports.txt` lists every function the module imports, and CI fails on any change to that list.

Conventions: a u64 argument or field is a decimal string (a scalar argument also takes a `bigint`), and a result amount is a decimal string; bytes are `Uint8Array` (an instance of a subclass, such as Node's `Buffer`, is read through its own length, whatever its `length` getter says), and hex fields of the JSON forms are lowercase; a leg index is the number 0 (asset) or 1 (cash); a network is `"mainnet"` or `"testnet"`.

Funding instructions (added for the browser demo, I11): `validated.fundingInstructions({ context, creation_daa_source, party, kas_equivalent?, cap?, accept_the_risk? })` is the SDK's `impulse address`. It returns nothing until every check has passed, in this order: the creation checks, a mainnet creation DAA score that the caller marks as read from a node (`creation_daa_source: "node"`; a typed score on mainnet is `SDK_MAINNET_NEEDS_NODE`, as the command line refuses it), the two "Before funding" checks (a native KAS cash leg below the minimum output, `TX_BELOW_MIN_KAS`; a KCC-20 template that is no pinned kcc20.sil build, `SDK_TEMPLATE_UNPINNED`, below), the role check (below), the per-trade value cap, and every escrowed leg instantiated as a fundable vault. It then returns the terms hash, the template hash, the role check that passed, what the cap measured, and for each leg its vault address and script hash, `you_fund` (true when the party's role is the leg's depositor) and, for a native KAS leg the party funds, the funding URI `<vault address>?amount=<sompi>&impulse=<terms hash>`; a leg the party does not fund has no URI, and a caller shows its vault address with "send nothing". The cap is 10 KAS (`defaultValueCapSompi()`, decision D4, default); `cap` may only lower it; every v1 trade needs `kas_equivalent`, because the asset leg is a KCC-20 token (`SDK_VALUE_UNKNOWN`); a value above the cap is `SDK_VALUE_CAP_EXCEEDED`. `accept_the_risk: true` skips the value checks, as the command line's `--i-accept-the-risk` does, and together with a `cap` is `SDK_VALUE_CAP_INVALID`; the browser demo never sets it. This is the one cap of the Value cap section below, which the builders also apply, under the names `max_value` and `i_accept_the_risk`. `qrCode(text)` returns the QR code (error correction level M, as `impulse address` prints) as `{ width, modules }`, one byte per module, 1 for dark. The URI and the cap follow `crates/impulse-cli`; `cargo test -p impulse-wasm` compares the two on every golden vector (with its tokens pinned: the vectors as committed name a synthetic token that no funding instruction accepts). Whether wallets read the URI's `amount` as sompi is not yet checked against real wallets. The result also carries `expiry` (the expiry and the approximate time from the creation score to it at 10 DAA scores per second), `destinations` (the four destinations as the terms summary of spec/CLI.md reads them: a Kaspa address or KCC-20 owner, whom it pays as far as its script shows, and `pays_counterparty_or_authority`, true when it pays the key of the party that does not own it or the authority's, which gives the leg away because the contract lets those parties trigger a refund) and, per leg, `token_warnings` (`TOKEN_UNASSESSED` for every KCC-20 leg: this function reads no token artifact). The `destinations` marks are for a party reading the other side's terms; the role check below is what protects the party who funds.

Role check (added for the browser demo, I11 phase 2): `validated.roleCheck({ role, key, pins? })` is the check of spec/CLI.md ("Terms summary and role check") that the command line runs in `terms new`, `address` and `verify`. `role` is `"buyer"` or `"seller"`, `key` the caller's x-only public key, and `pins` (`{ receive?, refund? }`, each a pin text or null) names a destination the caller controls that is not their key, as a Kaspa address of the terms' network in canonical form or `kcc20:<pubkey|script_hash|covenant_id>:<64 hex digits>`. It refuses unless the key is the role's party key in the terms (`SDK_ROLE_KEY_MISMATCH`), every pin parses (`SDK_DESTINATION_PIN_INVALID`), and each of the role's two destinations (the buyer's delivery and refund, or the seller's proceeds and refund) pays the key, equals its pin, or is off chain, and none pays the counterparty's key or the authority's, which no pin accepts (`SDK_DESTINATION_NOT_MINE`). It returns the role, the key, the leg the role funds and one line per destination. `fundingInstructions` runs it itself. `cargo test -p impulse-wasm` compares it with the command line's `check_party` and `parse_pin` on every vector for both roles, on the attack terms, and on the pin spellings.

Terms text (added for the browser demo, I11): `Terms.fromFileText(text)` reads the text of a terms document: the JSON form of terms, a terms file (`terms`, `canonical`, `terms_hash`) or a golden vector file (`name`, `description` and those three). The text is the argument, not a parsed value, because `JSON.parse` keeps the last of two equal keys and reads a number past 2^53 inexactly. It refuses JSON that names a key twice at any depth, a u64 given as a number, an unknown or missing key (`SDK_JSON_FORM`), and, for the two file shapes, a `canonical` or `terms_hash` that is not that of `terms` (`SDK_TERMS_INCONSISTENT`). `terms.requireSameAs(other)` refuses (`SDK_TERMS_INCONSISTENT`) unless both have the same canonical bytes, for terms read back from a form that must be the terms they were loaded from.

Creation context: `creation_daa` is the virtual DAA score at creation, read by the caller from a Kaspa node it trusts; the SDK has no node and takes the number as given. A `max_expiry_horizon_daa` the caller supplies replaces the default horizon, `defaultMaxExpiryHorizonDaa()`; leave the key out to use the default.

Addresses: as in Rust, only `FundableVault` has an `address` method, and only `instantiateForCreation`, which runs the value cap and the creation checks, makes one. In JavaScript this split is a rail for developers, not an enforced boundary: wasm-bindgen 0.2.100 does not check the class of `this`, so a method called through another class's object, for example `FundableVault.prototype.address.call(other)`, runs on the memory of `other`, whatever its class. That would also bypass the creation checks and the value cap (a funding address for a trade that `instantiateForCreation` refuses), and for a method that writes (`Ipst.prototype.addSignature`) it writes through the wrong class. The SDK does not guard against a caller that does this to itself. Call a method only on an object its own class returned, and keep untrusted code out of the page.

## Trading (phase 2)

The builders are methods of `ValidatedTerms`, so a builder works only from checked terms. Each takes JSON-form objects (the types are in `index.d.ts`: `UtxoJson`, `TokenUtxoJson`, `FeePaymentJson`, `Kcc20DepositJson`, `SettleLegsJson`, `DirectLegsJson`, `RefundEscrowJson`) and returns an `Ipst`, an unsigned document that carries the terms, the transaction, the UTXOs it spends and one signature slot per input (spec/IPST.md). UTXOs are what a node reports for them; the SDK has no node.

The flow, for any builder:

1. Build: `const ipst = validated.settle(legs, funding, currentDaa, value)`.
2. Check: whoever holds a document checks it before signing. `ipst.verifyAgainstTerms({ asset, cash }, currentDaa, value)` rebuilds the transaction with the builders from the document's own inputs and compares everything but the signatures, so a well-formed but wrong document (a skimmed output, a fee from a trade input, other budgets) is `IPST_TERMS_MISMATCH`. It returns the builder, the fee and the change for the signer to confirm, and applies the value cap (below). A signature is made outside the SDK, so the SDK cannot make a signer run this check; a signer that signs a received document without it signs without the cap.
3. Sign, outside the SDK: `ipst.slots()` names the key each slot needs, and `ipst.sighash(input)` the 32 bytes to sign (BIP-340 Schnorr, then the byte `0x01`, SIG_HASH_ALL, for 65 bytes). Signing happens where the key is, by the caller's own code; the SDK never takes a secret key. Or sign with the SDK's own `Wallet` (below), whose key is drawn and kept inside the module.
4. Store: `ipst.addSignature(input, signature)` verifies the signature against the slot and stores it.
5. Merge: each signer can return `ipst.toJson()`; `ipst.combine(otherText)` takes the signatures of another copy of the same document, verifying each, and refuses any difference but signatures (`IPST_CONFLICT`).
6. Assemble: `ipst.finalize()` (or `ipst.assemble([{ input, signature }])`) returns a `SignedTransaction` with `txid()` and `raw()`. `finalize` checks the masses and the relay fee again, because no signature covers an input's compute budget.

`raw()` is rusty-kaspa's borsh encoding of the transaction, the form `decodeRaw` reads. `rpcSubmitRequest(id, signed)` writes the node's `submitTransaction` request (below); a node, not this package, decides whether the transaction is accepted.

KCC-20 templates are passed as the text of the token's silverscript ABI artifact (the JSON `silverc` writes), by the object that needs one: `deposit.artifact`, `legs.asset_artifact`, `legs.cash.artifact`, `escrow.artifact`. It is parsed and checked on each call against the KCC-20 layout and, per leg, against the template hash and lengths the terms name (`TX_TOKEN_TEMPLATE`); text over 64 KiB is refused unparsed. `kcc20Template(artifact)` gives the triple a leg of the terms names a token by, and `kcc20ScriptPublicKey(artifact, state)` the scriptPublicKey of a token UTXO in a state.

Fund builders take a creation context instead of a DAA score: `creation_daa` is the current DAA score, read by the caller from a node it trusts, and the creation checks run first. Settle and Direct take `currentDaa`, a decimal string or a bigint; they refuse a trade that can no longer settle by its expiry (`TX_EXPIRED`).

### Value cap

The SDK refuses a trade above a per-trade cap of 10 KAS (owner decision D4, default), before it does anything else. The cap holds in every builder (`fundKas`, `fundKcc20`, `settle`, `refund`, `direct`), in the call that gives out a funding address (`instantiateForCreation`, the only path to `FundableVault.address()`), in the calls that check a counterparty's addresses (`verifyAddresses`, `beforeFunding`), and in the check a signer runs on a received document (`verifyAgainstTerms`). Each takes the declaration as its last argument. The value is the larger of the KAS legs, the value the caller declares, and the native KAS the call itself moves:

```js
{ kas_equivalent: "100000000" }          // the KAS value of the larger leg, in sompi
{ kas_equivalent: "1", max_value: "50000000" }   // a lower cap
{ i_accept_the_risk: true }        // the only way to lift the cap
```

In v1 the asset leg is always a KCC-20 token whose value the SDK cannot know, so `kas_equivalent` (nonzero) is required for every trade unless the cap is lifted (`SDK_VALUE_UNKNOWN`); it is the caller's word and nothing checks it. The native KAS a call moves counts as a KAS leg does: the fee in every builder and in `verifyAgainstTerms` (the fee the document pays), and, in `fundKcc20`, the carrier plus the authorizer, which go into the vault with the token and on to the receiving party on settle. A value above the cap is `SDK_VALUE_CAP_EXCEEDED`. `max_value` can only lower the cap, and together with the flag that lifts it is `SDK_VALUE_CAP_INVALID`. The cap applies to refunds too, so a refund needs a declaration like any other builder.

Where the cap does not hold: `instantiateExisting` (a vault of an existing trade has no funding address), and the operations on a document that carry a signature in or out (`Ipst.fromJson`, `sighash`, `addSignature`, `combine`, `finalize`, `assemble`), because a signature is made outside the SDK and nothing here can see what a signer intends. A wallet or signer layer must therefore call `verifyAgainstTerms` with its own declaration before it signs, and show the fee and the change it returns. The rule is the one of spec/CLI.md, with two differences, both stricter: the native KAS a call moves is counted, and `max_value` together with the lift flag is refused where the CLI spec says only the flag lifts. A copy of the rule is in `impulse-cli`; both copies are to move into impulse-core (see the increment report).

## Wallet, review, node forms and plans (I11 phase 2)

For the browser demo, in Rust like the rest (`wallet.rs`, `review.rs`, `rpc.rs`, `plan.rs`).

`Wallet.generate()` draws 32 bytes from `crypto.getRandomValues` (one call), holds them in a zeroed-on-drop buffer inside the module, and gives JavaScript an opaque handle: `publicKey()` (x-only, 64 hex digits), `address(network)` (its P2PK address, where to send it KAS), `sign(ipst, options)`, `wipe()` and `isWiped()`; `free()` drops it. No member returns the key, a string of it or anything derived but the public key and signatures, and a test lists the members of the class. `wipe()` and `free()` zero the buffer; the test suite measures the module's linear memory for the 32 bytes: one copy while the wallet holds it, none after a wipe or a free (Node 22, this build; the browser's own copy of the random bytes, and anything an engine keeps outside the module's memory, are out of reach, and wasm memory is not cleared when a page unloads). Signing is deterministic BIP-340 and draws no randomness.

`wallet.sign(ipst, { artifacts, current_daa, value, mainnet, pins?, held?, change?, max_fee?, max_topup?, carrier?, authorizer? })` does what the command line's `ipst sign` does, in this order, and returns `{ ipst, signed_inputs }` (the document passed in is not changed): the mainnet choice (`SDK_SIGN_MAINNET_NOT_EXPLICIT`, `SDK_SIGN_NETWORK_MISMATCH`); that the key signs an input that lacks its signature (`SDK_SIGN_NOTHING_TO_SIGN`); that the document is what the builders make from its own inputs and is within the value cap (`verifyAgainstTerms`: `IPST_TERMS_MISMATCH`, `SDK_VALUE_CAP_EXCEEDED` and the rest); for a funding, the checks of step 6 of `ipst sign` (below); the role check when the key is the seller's or the buyer's, with `pins` for that party (`SDK_DESTINATION_NOT_MINE`); the payer's side (`payer.rs`, steps 9 and 10 of spec/CLI.md); then the signature, which is verified against the wallet's public key before it is stored (`SDK_SIGN_SELF_CHECK_FAILED`). A wiped wallet is `SDK_WALLET_WIPED`; a browser without randomness is `SDK_WALLET_RANDOM`.

The payer's side. The terms check fixes every trade output from the trade inputs, not what the fee inputs pay into them: a counterparty who funds a vault's authorizer or a carrier below its minimum makes the builder top the pass-through output up, and the top-up comes out of the fee payer's inputs on top of the fee. A wallet that signs a fee input therefore checks, before it signs: that the change output, if there is one, pays `change` (an address of the terms' network; without it the wallet's own key; `SDK_SIGN_CHANGE_NOT_MINE`); that the fee is at most `max_fee`, by default twice the minimum relay fee, and without a `max_fee` that it signs at most three fee inputs (`SDK_SIGN_FEE_TOO_HIGH`); and that in a settle, a refund or a Direct transaction the cost beyond the fee, the top-up, is at most `max_topup`, by default none (`SDK_SIGN_TOPUP_TOO_HIGH`). Whatever input it signs that holds its own funds, the wallet also checks the outflow, what those inputs hold less what comes back to it (the change, a funding's token change), against what the trade takes from it (the KAS cash of a Direct trade, `carrier` KAS, by default the minimum of a KCC-20 output, for each token it gives, a funding's deposit) plus `max_fee` and `max_topup` when it pays the fee (`SDK_SIGN_OUTFLOW_TOO_HIGH`), and against the value cap (`SDK_VALUE_CAP_EXCEEDED`). `max_fee`, `max_topup`, `carrier` and `authorizer` are u64 decimal strings. The builders take the same `change` in their funding (`{ payer, fee, change? }`), so the document pays the address the signer will accept.

Keys that live only in wallets. A wallet's key exists only in the module's memory and is lost with the page, and no call of the SDK spends from it but the fee inputs and the token inputs of the transactions it signs. So `held` (public keys, at most 8, besides the wallet's own) names the keys of the wallets of a page, and on a mainnet document: the role check refuses a destination of the user's role that pays one of them, pinned or not (`SDK_DESTINATION_IN_WALLET`; `roleCheck`, `fundingInstructions` and `sign` take `held` in the party or the options), a change that pays one is refused, and so is every other output that pays one (the vault's authorizer comes back to the seller's key whatever the terms say). On testnet nothing is refused, and `roleCheck` reports the destinations (`in_wallet`, and a sentence in `lines`) and the review marks the outputs. The remedy is a pin, and a `change`, naming an address the person controls elsewhere.

`ipst.review(artifacts, currentDaa, value, held?)` is what a signer reads before signing: the title (what the document does, in words; for external cash it says the cash is paid outside Kaspa and the authority's signature attests it), the terms hash and nonce of the trade it belongs to, each input and output with amount, scriptPublicKey, address and what the terms say it is (a label from an exact match against the four destinations, the parties' keys, the vaults and the escrowed tokens; "not named by the terms" otherwise), whose key each signature is for (`signer_role`: the seller, the buyer, the authority, or none of them), the fee, the minimum relay fee, the masses, the payer cost beyond the fee (`payer_cost`, `payer_cost_text`), the lock time with the DAA score from which the transaction is final and whether a node at `currentDaa` admits it (`submit_ready`), the inputs still unsigned, and `notes`: a sentence for the authority's signature, and for outputs that pay a key in `held` (`held_key` on the output, `held_outputs`, `held_amount`). It runs `verifyAgainstTerms` first, so a document the builders would not make, or above the cap, has no review. The time estimates (`wait`) are at the nominal 10 DAA scores a second.

The node's JSON over wRPC (a kaspad started with `--rpclisten-json`): `rpcRequest(id, method, argument)` writes a request (`rpcMethods()` lists the six calls: `getServerInfo`, `getBlockDagInfo`, `getUtxosByAddresses`, `submitTransaction`, `getMempoolEntry`, `getVirtualChainFromBlockV2`), `rpcSubmitRequest(id, signed)` the submit request, `rpcReply(text, id, method)` reads a reply as text (a number past 2^53 is exact; every u64 comes back as a decimal string) and refuses one that answers another request or says it failed, with the node's words quoted and cut (`SDK_RPC_REPLY`), `rpcTransactionReply(text, id, method, txid)` reads the two calls that return a transaction and refuses one that does not hash to `txid` (`SDK_TXID_MISMATCH`); the one error that is an answer, kaspad's `Transaction <txid> not found` to `getMempoolEntry`, is `SDK_RPC_NOT_FOUND`, and every other error of the node stays `SDK_RPC_REPLY`, and `rpcSubmitReply(text, id, signed)` returns the ID the node accepted, which must be the submitted transaction's. `checkNodeUrl(url, network)` is the command line's transport rule (`ws://` or `wss://`; on mainnet `wss://` or `ws://` to `127.0.0.1` or `localhost`: `SDK_NODE_URL_INVALID`, `SDK_NODE_INSECURE`), except that `ws://` to the IPv6 loopback literal `[::1]` is refused on mainnet, which the command line takes (the demo page's Content-Security-Policy cannot name an IPv6 literal) and `checkNode(info, network)` refuses a node on another network or not synced (`SDK_NODE_NETWORK_MISMATCH`, `SDK_NODE_NOT_SYNCED`). `decodeFetched(fetched, txid, network)` decodes a transaction read from a reply, bound to the scriptPublicKeys its inputs spend when the node gave all of them (the accepted transactions of `getVirtualChainFromBlockV2` at full verbosity do; the mempool entry does not, so that decoding says `bound: false`). The forms are written from the pinned source and checked, natively, against the real `kaspa-rpc-core` types; nothing has been run against a node on a network.

The plan builders work from the text of a `getUtxosByAddresses` reply, so that a list of UTXOs never passes through JavaScript: `validated.settleAddresses(artifacts, payerKey)`, `refundAddresses(leg, artifacts, payerKey)` and `directAddresses(artifacts, payerKey)` name the addresses to ask about; `settleFromReply(artifacts, reply, { payer, fee }, currentDaa, value)`, `refundFromReply(leg, signer, withToken, artifacts, reply, funding, value)` and `directFromReply(...)` choose the UTXOs by the rules at the top of `plan.rs` (the largest plain UTXO at a vault, the exact token state, the exact KAS amount, lowest outpoint among equals; the payer's own plain P2PK UTXOs for the fee, largest first, never one a leg uses) and call the builder. `fee` is a sompi amount or `"auto"`, the minimum relay fee of the transaction's mass and a tenth more. A UTXO that is not among those the node reported is `SDK_UTXO_NOT_FOUND`.

The buyer's funding of a KAS cash vault is a plan builder too: `validated.fundCashAddresses(artifacts, payerKey)` names the addresses to ask about (the cash vault, the asset vault with the token escrowed in it, and the payer's own), and `fundCashFromReply(artifacts, reply, { payer, fee, change? }, currentDaa, value)` builds `fund_kas`, one output of exactly the cash amount at the cash vault, paid by the payer's own plain P2PK UTXOs (largest first, enough for the deposit and the fee with a change of zero or at least the minimum output) with the change at `change` or back at the payer's key. `currentDaa` is the node's score, the creation DAA score of the creation checks (the trade cannot be created at or after its expiry, `TERMS_EXPIRY_NOT_AFTER_CREATION`). It refuses, in the order of the command line's `fund build` where the command line has the check: a native KAS cash leg below the minimum output (`TX_BELOW_MIN_KAS`; the command line's `CLI_KAS_LEG_BELOW_MIN`); a `payer` that is not the terms' buyer key (`SDK_FUND_NOT_YOUR_LEG`, the command line's `CLI_FUND_NOT_YOUR_LEG`); a leg with no vault (Direct terms, external cash: `TEMPLATE_NO_VAULT`); a KCC-20 cash leg (`TX_WRONG_MODE`, a limit of the SDK, not the command line's rule: the command line funds a token leg with the depositor's token UTXOs, which the SDK does not choose); a KCC-20 leg whose template is not a pinned kcc20.sil build (`SDK_TEMPLATE_UNPINNED`, no override, see below); then, from the reply, a cash vault that already holds a UTXO of exactly the cash amount, which is the deposit a settle takes (`SDK_FUND_ALREADY_FUNDED`), and an asset leg that is not funded, that is no authorizer at the asset vault or no token in the exact state the leg needs (`SDK_FUND_ASSET_NOT_FUNDED`): the buyer's only way to take a deposit back unaided is a refund signed by the funding key, from the expiry in earmarked mode, so cash is not funded before the seller's asset leg is on the node, and not twice. The value cap holds as for every builder. The buyer's wallet signs the result with `wallet.sign`, which checks the document and what the signer commits (the deposit and the fee) as for any funding, and the funding checks of step 6 of `ipst sign` (below). The review of the document (`ipst.review(artifacts, currentDaa, value, held)`) carries `exit_note`, also the first of its `notes`: how the deposit comes back if the trade never settles (a refund of the cash leg signed with the buyer's key, from DAA score expiry plus one in earmarked mode and at any time in revocable mode, which the seller or the authority can also trigger and which pays the buyer's refund destination whoever signs it) and, when the buyer's key is among `held`, that closing or reloading the page, or wiping the wallet, destroys that way out. A fee of `"auto"` is not the command line's automatic fee: the command line builds at the minimum relay fee of the transaction, this builder at that minimum and a tenth more (rounded up), because it chooses the inputs for the fee and one more input raises the minimum. The same inputs and a typed fee give the same document byte for byte on both (a native test builds both with the command line's `build_with_fee`).

"Before funding" (spec/CLI.md): a KCC-20 leg whose template (hash, prefix length, suffix length) is not one of the pinned kcc20.sil builds, `pinnedKcc20Templates()` (the sixteen of silverscript v1.0.0, `maxCovIns` and `maxCovOuts` from 1 to 4, in the order of `PINNED_KCC20_TEMPLATES`), is never funded: `fundingInstructions` (and with it the funding URI and the QR code), `fundCashAddresses`, `fundCashFromReply` and the signature of a funding by `wallet.sign` refuse it with `SDK_TEMPLATE_UNPINNED`, as `impulse address`, `fund build` and `ipst sign` refuse it with `CLI_TEMPLATE_UNPINNED`, because the builders' compute budgets are measured for kcc20.sil only and a settle or refund of another token may not build. The golden terms vectors name a synthetic token that is no kcc20.sil build, so they get no funding instruction either. `wallet.sign` of a funding (`fund_kas` or `fund_kcc20`) also checks, after the terms check and before the payer's checks, that the wallet's key is the leg's depositor (`SDK_FUND_NOT_YOUR_LEG`), that the terms pass the creation checks at the score it is told, with every escrowed leg a fundable vault (`TERMS_*`, `TEMPLATE_*`), and the two checks above. For a KCC-20 funding it also checks that the KAS on the escrowed token (output 0) and on the authorizer (output 1) are the amounts the signer confirms with the options `carrier` and `authorizer`, by default the minimum of a KCC-20 output and of a KAS output, as `ipst sign --carrier --authorizer` does (`SDK_SIGN_DEPOSIT_MISMATCH`; `authorizer` for any other document is `TX_WRONG_MODE`). The terms check takes both amounts from the document, so only the signer can confirm them. The page builds no KCC-20 funding.

## Verifying and decoding (phase 2)

- Before funding: `validated.verifyAddresses(context, { asset, cash })` recomputes each leg's address from the terms and compares it with the one offered; `validated.beforeFunding(...)` adds the token warnings. A warning is data read from the evidence supplied, never a statement that a token is safe, and `token_legs_assessed: false` must not be shown as checked. The token artifact must come from the token publisher's reproducible build, never from the counterparty.
- After a spend: `validated.verifyRevealedScript(leg, script)` and `validated.verifySpentInput(leg, signatureScript, spent)`, where `spent` is the scriptPublicKey of the UTXO the input spends as the node reports it, never one the counterparty supplies.
- `decodeRaw(raw, spent, network)` finds the vault inputs of a transaction, reads back their terms, leg and entry, and reports what each does. It is bound to the scriptPublicKeys the inputs spend, one per input, because the transaction ID does not commit to signature scripts. `decodeRawUnbound` skips the binding and says so (`bound: false`). A vault input refused on its own comes back in `refused` beside the legs that decoded.
- Messages may quote counterparty text, escaped to printable ASCII but not for HTML. Match on `code`; escape text for the medium you write to. A decode refusal of one input starts its message with `input N: `, before the code.

## Template v2 trades (I16)

Beside the v1 classes, and with the same argument forms, the package exposes the ImpulseVault template v2 surface of spec/V2.md 6.5: `TermsV2` (the JSON form of spec/V2.md 5.4, `encode`, `decode`, `termsHash`, `validateStructure`), `ValidatedTermsV2` (`vaultAddresses(context, value)` for every leg, `minV2`, and the builders `fundKas(leg, ...)`, `fundKcc20(leg, ...)`, `settle(legs, ...)` with one element per leg in leg order, and `refund(leg, signer, ...)` with `signer` a leg number or `"authority"`), `IpstV2` (the document of version 2, with the members of `Ipst` and `abovePreToccataCap`), and `termsV2Version`, `maxLegs`, `capsV2`, `templateHashV2`, `v2ErrorCodes`. The value cap holds before every v2 builder, `vaultAddresses` and `verifyAgainstTerms`; for terms v2 the trade value is the larger of the declaration (the KAS value of all legs together) and the KAS legs together. `Ipst.fromJson` refuses a document of version 2 and `IpstV2.fromJson` one of version 1 (`IPST_UNSUPPORTED_VERSION`). Template v2 is not frozen before the I17 merge (D30), so no v2 trade is for mainnet value before then.

## Refusals

Every refusal throws an `Error` named `ImpulseError` with a stable `code`. Match on the code, never on the message.

An error carries `nodeError: true` only when the node itself sent it in answer to the very request: a well-formed reply with the request's id and an `error` member (`SDK_RPC_REPLY`, or `SDK_RPC_NOT_FOUND`). A caller that has sent a transaction needs it: the node refused it, so nothing was taken, as against an answer that cannot be read (another request's id, text that is not JSON, a reply with no params, `SDK_TXID_MISMATCH`), after which what the node did with the transaction is unknown. The property is absent on every other error.

- `TERMS_*`, `TEMPLATE_*`, `TX_*`, `IPST_*`, `VERIFY_*` and `DECODE_*`: impulse-core's codes, unchanged (spec/ENCODING.md, spec/TEMPLATE.md, spec/TRANSACTIONS.md, spec/IPST.md, spec/VERIFY.md).
- `SDK_VALUE_UNKNOWN`, `SDK_VALUE_CAP_EXCEEDED`, `SDK_VALUE_CAP_INVALID`: the value cap above, one rule for the builders and for `fundingInstructions`.
- `SDK_TERMS_INCONSISTENT`: a terms file's `canonical` or `terms_hash` is not that of its `terms` (the command line's `CLI_TERMS_FILE_INCONSISTENT`), or terms differ from the terms they were to equal (`requireSameAs`).
- `SDK_ROLE_KEY_MISMATCH`, `SDK_DESTINATION_NOT_MINE`, `SDK_DESTINATION_PIN_INVALID`, `SDK_DESTINATION_IN_WALLET`: the role check above, and the mainnet refusal of a destination, a change or an output that pays a key held only in a wallet.
- `SDK_WALLET_WIPED`, `SDK_WALLET_RANDOM`, `SDK_SIGN_MAINNET_NOT_EXPLICIT`, `SDK_SIGN_NETWORK_MISMATCH`, `SDK_SIGN_NOTHING_TO_SIGN`, `SDK_SIGN_SELF_CHECK_FAILED`, `SDK_SIGN_CHANGE_NOT_MINE`, `SDK_SIGN_FEE_TOO_HIGH`, `SDK_SIGN_TOPUP_TOO_HIGH`, `SDK_SIGN_OUTFLOW_TOO_HIGH`, `SDK_SIGN_DEPOSIT_MISMATCH`: the wallet. `SDK_SIGN_SELF_CHECK_FAILED` has no case in the TypeScript suite, because no input makes a correct signature fail; a native test drives it with a hook that exists only in test builds.
- `SDK_NODE_URL_INVALID`, `SDK_NODE_INSECURE`, `SDK_NODE_NETWORK_MISMATCH`, `SDK_NODE_NOT_SYNCED`, `SDK_RPC_REPLY`, `SDK_RPC_NOT_FOUND`, `SDK_TXID_MISMATCH`, `SDK_UTXO_NOT_FOUND`: the node forms and the plan builders. `SDK_FUND_NOT_YOUR_LEG`: `fundCashAddresses`, `fundCashFromReply` or the signature of a funding for a payer that is not the leg's depositor. `SDK_TEMPLATE_UNPINNED`: a funding instruction, a cash funding or the signature of a funding for a KCC-20 template that is no pinned kcc20.sil build. `SDK_FUND_ASSET_NOT_FUNDED`, `SDK_FUND_ALREADY_FUNDED`: `fundCashFromReply` while the seller's asset leg is not on the node, or the cash vault already holds the deposit.
- `SDK_MAINNET_NEEDS_NODE`: `fundingInstructions` on mainnet with a creation DAA score not marked as read from a node. `SDK_QR`: the text of `qrCode` does not fit a QR code.
- `SDK_ARGUMENT_TYPE`: an argument is not of the JavaScript type the API declares, for example a hex string where a `Uint8Array` is expected, or a leg index that is not an integer number.
- `SDK_JSON_FORM`: a terms object, creation context or network name breaks the JSON form: a missing or unknown key, a value of the wrong JSON type, a string outside its enumeration, hex that is not lowercase or not the right length, or a u64 that is not a canonical decimal string. Rust reads the JavaScript value itself, not its `JSON.stringify` text, so a value JSON cannot hold is refused where it stands rather than turned into `null` or left out: `undefined` (leave an optional key out instead), NaN, the infinities, -0, a bigint, an array, a Date, a class instance or boxed value, a getter, a symbol key or a non-enumerable property. `toJSON` is never called. Also refused, before any string is copied into the module's memory: a value past bounds no terms come near (more than 2^18 characters in all its keys and strings, more than 64 keys in one object, objects nested more than four deep), and a network name longer than 64 characters. The phase 2 arguments also take plain arrays (the prototype chain of an array, own elements that are enumerable data properties, no hole, no other property; at most 256 elements, five levels of nesting) and refuse every other array, a hole, an array subclass and a sparse or extended array; terms and contexts still take no array. An IPST text over 2^23 characters is refused before it is copied, one with more than 256 inputs or more than 256 outputs before it is read (the reader is quadratic in the input count), and an artifact over 64 KiB before it is parsed.

A refusal message quotes at most 32 characters of a string the caller passed.

Each terms value has one rendered JSON form: `toJson` writes the keys in field order. Parsing is strict about keys and values (every key present, no other key, one spelling per value) but not about key order, which is not significant. It checks form only; the terms checks run in `validateStructure`.

## Building and testing

From `crates/impulse-wasm/`, `./ci.sh` runs the whole gate (a step of `scripts/ci-local.sh`): tool pins, clippy on wasm32, `wasm-pack test --node`, the package build, `tsc` and `node --test "test/*.test.ts"`, with every process's draws of randomness counted against the keys its tests asked for. Most TypeScript tests sign with a runtime throwaway key (`@noble/curves`, a dev dependency, not shipped); the wallet tests use `Wallet` keys and learn them only by recording the bytes the module draws, to look for them where they must not be. `test/fakenode.ts` is an offline stand-in for a node (its header says what it checks and what it does not). The 32-byte secret buffer is zero-filled after the test; the BigInt copies that `@noble/curves` makes while signing cannot be erased from JavaScript and live until garbage collection. The keys are throwaway, are never written anywhere, and no key literal is in the tests. Every call a trade test makes is also run by the native build of the same operations (`cargo test -p impulse-wasm --lib ops_tests::oracle -- --ignored`, run by the tests themselves, so `cargo` must be on the path), and the answers must be equal byte for byte. It needs wasm-pack 0.14.0, the wasm-bindgen CLI at the version in `Cargo.lock` (0.2.100), Node 22.18 or later, and an LLVM `clang` and `llvm-ar` for the C part of secp256k1 on wasm32. `./ci.sh` is the only build of the package: it remaps the cargo home and the repository out of the source paths rustc writes into the module, and fails if the module still holds a path of the build machine. Publish only a package that CI built.
