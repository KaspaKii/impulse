# Impulse v0.2 design: basket, partial and hashlock settlement

Draft, 11 October 2026, increment I16 (design step for I16, I17 and the Kaspa side of I18), revised the same day after the red team of section 16. Companion to `IMPULSE-SPEC.md` (the v0.1 design, which stays authoritative for everything this file does not change), `ENCODING.md`, `TEMPLATE.md`, `TRANSACTIONS.md`, `VERIFY.md` and `ERRORS.md`. This file is the authoritative v0.2 design once the owner accepts it; until then it is a draft and nothing on `release/v0.2` may contradict it without a spec change.

## 0. How to read this file

Every factual statement about the toolchain, the chain or a size carries one of three marks:

- **(measured)**: observed in this session from the pinned sources or the pinned compiler, with the method given. "(measured, source)" means read from the pinned source code, with the file named; it is not a run. Raw data for the compiler measurements is committed in `docs/measurements/v2-probe/` (`run.sh` reproduces `results.txt`).
- **(modelled)**: computed from a formula and stated assumptions. It is an estimate for design choices, never a number to publish. Each one names the increment that replaces it with a measurement.
- **(asserted)**: taken from a document or a third party and not checked here.

Statements of the design itself (what the contract requires, what the builders refuse) carry no mark: they are the specification.

Owner decisions this design depends on are D29 to D35 and D37 to D46, each with a default; this design follows the defaults (section 14). Questions still open after the red team are listed as such in section 16; none is silently dropped.

What v0.2 does not do, so the v0.1 out-of-scope list stays true: Impulse does not compute a net. A "10-line bilateral net" (I16, the original wording) is a list of legs the parties agreed; template v2 settles the list it is given. Impulse executes an agreed list of legs and provides no legal netting, novation or statutory settlement finality. "Net" stays out of product names, CLI commands and flags, vector names and receipt fields.

What each v0.2 flow promises is stated once, in section 4.8 (finality and wording), and every receipt, verify output and CLI message uses those words.

- A v1 trade funded before or after v0.2 settles and refunds with the v1 builders and template exactly as before. Nothing in v0.2 reads, re-encodes or migrates a v1 trade.
- How v1 software meets v0.2 data: a terms v2 or hashlock encoding starts with a version byte that the v1 decoder refuses (`TERMS_UNSUPPORTED_VERSION`; the hashlock terms carry their own tag, so their hash can never equal a v1 hash). A v2 or hashlock vault script ends with another suffix than v1's, so the v1 decoder refuses it as `TEMPLATE_NOT_IMPULSE_VAULT` and the v1 verifier as `VERIFY_TEMPLATE_MISMATCH`. An IPST of version 2 is refused by a v1 reader as `IPST_UNSUPPORTED_VERSION`. All three are the existing v1 behaviour for unknown input, not new rules.
- Error codes: v0.2 only appends (section 8). No v1 code is renamed, reused, widened or renumbered.
- The design principles of `IMPULSE-SPEC.md` hold for v2 with two stated amendments, carried to that file at the v0.2 release (section 15): principle 4 (exact amounts) gains the partial-settlement rule of section 4.6, and principle 6 (one template, two entries) becomes "each template has two entries" now that v0.2 adds two templates.

## 3. Facts at the pinned revisions this design rests on

### 3.1 rusty-kaspa a41a333 (KIP-20 covenant IDs and opcodes)

Method: read from the pinned checkout `~/.cargo/git/checkouts/rusty-kaspa-410e06d1fde91a92/a41a333` and diffed against `~/rusty-kaspa-v2.0.1` (cfafeb4). `crypto/txscript/src/opcodes/mod.rs`, `crypto/txscript/src/covenants.rs` and `consensus/core/src/hashing/covenant_id.rs` are identical in both (measured).

- KIP-20 opcodes exist and are enabled when covenants are enabled (measured): `OpAuthOutputCount` 0xcb, `OpAuthOutputIdx` 0xcc, `OpInputCovenantId` 0xcf, `OpCovInputCount` 0xd0, `OpCovInputIdx` 0xd1, `OpCovOutputCount` 0xd2, `OpCovOutputIdx` 0xd3, `OpOutputCovenantId` 0xd5, `OpOutputAuthorizingInput` 0xd6. An input or output without a covenant reports the zero covenant ID (measured).
- Consensus rule for an output that carries a covenant binding `(covenant_id, authorizing_input)` (measured, `CovenantsContext::from_tx`): if the authorizing input carries the same covenant ID, the output is a continuation and is counted by `OpCovOutputCount` and `OpCovOutputIdx`; otherwise it is a genesis, and the ID must equal `covenant_id(outpoint of the authorizing input, the group's authorized outputs)` (BLAKE2b-based, over the outpoint, then each output's index, value, script version and script). Consensus runs no script for a genesis; the input's own script decides what continuations it allows.
- Consequence: the covenant ID of a vault funded as a genesis depends on the funding outpoint, so it cannot be part of the terms. A vault reads its own ID at spend time (`OpInputCovenantId(this.activeInputIndex)`), as `KCC20Minter` reads its controller ID.
- `OpMul`, `OpDiv`, `OpMod` are enabled post-Toccata, on 64-bit signed integers, and fail the script on overflow, on division by zero and on modulo by zero (measured, source). `OpSHA256` exists and charges 1 script unit per byte hashed; Blake2b charges 2 (measured, `HashOpcodePricing`).
- Limits post-Toccata (measured, `crypto/txscript/src/lib.rs`): script size 1,000,000 bytes, element size 1,000,000 bytes, stack 244 items. Signature script per input at most 250,000 bytes (`NEW_MAX_SIGNATURE_SCRIPT_LEN`) and scriptPubKey at most 10,000 bytes (`max_script_public_key_len`) (measured, source, `consensus/core/src/config/params.rs`). Every vault and token output is a P2SH scriptPubKey of 35 bytes (measured, source: silverscript `std/builtins.sil`, `validateOutputStateWithInputTemplate` "require the selected output to use the matching P2SH scriptPubKey"); the templates and their state travel in the spending input's signature script, which the 250,000-byte limit bounds.
- Mass (measured, source, `consensus/core/src/mass/mod.rs`, `calc_non_contextual_masses`): transient mass is 4 grams per serialized byte; compute mass is 1 gram per serialized byte, plus 10 grams per byte of each output's scriptPubKey and its 2-byte version, plus 100 grams per compute-budget unit; a budget unit is 10,000 script units; the per-input budget field is a u16. Storage mass is contextual (KIP-9, plurality and values).
- Mass limits (measured, source). There is no fixed per-transaction standard cap after Toccata: `mining/src/mempool/check_transaction_standard.rs` applies `MAXIMUM_STANDARD_TRANSACTION_MASS_PRE_TOCCATA = 100,000` per dimension only until 30 minutes before Toccata activation and returns no cap after it; from then on the per-transaction ceiling is the block-fit check (`mining/src/mempool/check_transaction_limits.rs`) against `Params::block_mass_limits()`. For mainnet, TN10 and the other networks in `params.rs`, `prior_block_mass_limits` is a shared 500,000 for storage, compute and transient, and `block_mass_limits().after()` replaces transient with `new_transient_mass_limit = 1,000,000`; compute and storage stay 500,000 (`mempool_block_mass_limits` asserts they do not change). A transaction at a dimension's block limit fills that dimension of a block alone, so the v2 caps sit below the limits (section 6.2, D37).
- Standardness (measured, source, `check_transaction_standard.rs`): each P2SH input may carry at most `MAX_STANDARD_P2SH_SIG_OPS = 15` signature operations as counted by `post_toccata_p2sh_sig_scanner`. Not yet checked against the v2 and hashlock templates; I16 and I18 test it (section 11).

### 3.2 silverscript v1.0.0 (3ed9733), pinned silverc

Method: compiling the probes in `docs/measurements/v2-probe/` with the pinned silverc (provenance checked by `run.sh` as `scripts/build-template.sh` does).

- Contract state may hold a `byte[]` field longer than 255 bytes and a runtime-bounded `for` loop over it; `byte[].slice`, indexing a `byte[]` to get a `byte`, `int(byte[8](...))`, `%`, `/`, `sha256`, `OpCovOutputCount` and `OpCovOutputIdx` all compile (measured). `int(byte[8](...))` emits no conversion opcode (measured: `int_cast_probe.sil` compiles to `OpSubstr` followed directly by the comparison, with no `OpBin2Num`), so the eight bytes reach the numeric opcodes exactly as v1's fixed-width state integers do, which v1's engine tests exercise. The engine accepts them (measured, source, `crypto/txscript/src/data_stack.rs`): `pop_items` decodes with `deserialize(!self.covenants_enabled)`, so with covenants enabled minimal encoding is not enforced and an 8-byte little-endian number with sign in the top bit of byte 8 is read as is; a value with that bit set is negative. Amounts therefore stay at most `i64::MAX`, which section 5.3 enforces. The first I16 engine test still pins this, with boundary tests for an amount of `i64::MAX` (accepted) and a crafted state field with the top bit set (read as negative, so the leg fails `[P2]` to `[P4]` or a delivery require; the test pins which).
- `validateOutputState` refuses, at compile time, a state field of variable length (measured: `continuation_state_probe.sil` for `byte[]`; an uncommitted variant with `byte[32][]` gave the same refusal). A template whose state holds the leg list therefore cannot continue into a changed state. This is why partial settlement continues with unchanged state (section 4.6).
- `for` loops are unrolled to their compile-time bound, so template size grows with the bound (measured). Probe of the v2 vault with the settle entry as specified and a reduced refund (results.txt):

| MAX_LEGS | Probe bytecode, bytes | Template suffix, bytes |
| --- | --- | --- |
| 2 | 3,139 | 2,435 |
| 4 | 4,265 | 3,561 |
| 10 | 7,643 | 6,939 |
| 16 | 11,021 | 10,317 |

  The settle loop costs 563 bytes per unit of MAX_LEGS (measured, from the table). The real template is larger: its refund carries v1's token logic (modelled at about 1,000 more bytes; I16 measures the real template). For comparison, the v1 template is 2,938 bytes of bytecode with the placeholder state (measured, committed artifact).
- The silverscript tutorial warns that the runtime check of a loop's range "may be removed in a later version" (asserted, `docs/TUTORIAL.md`, "For Loops"). The v2 contract therefore checks its loop bound itself (`[V1]`, `[V3]`).

### 4.2 State

Each field is one data push, as silverscript-abi encodes state (v1 rules; the `legs` push is 374 bytes or more and uses `OP_PUSHDATA2`). Integers are 8-byte fixed-width script numbers, as in v1.

| # | Field | Type | Value |
| --- | --- | --- | --- |
| 1 | version | byte | 2 |
| 2 | network | byte | 0 mainnet, 1 testnet |
| 3 | nonce | byte[8] | nonce, u64 little-endian |
| 4 | hasAuthority | bool | authority_key present |
| 5 | authorityKey | pubkey | authority_key, or 32 zero bytes |
| 6 | legCount | int | N, 2 to MAX_LEGS |
| 7 | legs | byte[] | the N leg records, in terms order, `LEG_RECORD` bytes each |
| 8 | hasEarliest | bool | earliest_daa present |
| 9 | earliestDaa | int | earliest_daa, or 0 |
| 10 | expiryDaa | int | expiry_daa |
| 11 | fundingMode | byte | 0 revocable, 1 earmarked |
| 12 | tradeRef | byte[32] | trade_ref |
| 13 | lotCount | int | partial: lot_count (at least 2); otherwise 1 |
| 14 | minLot | int | partial: min_lot; otherwise 1 |
| 15 | legIndex | int | this vault's leg, 0 to N - 1 |

Leg record, 187 bytes:

| Offset | Bytes | Field | KCC-20 leg | KAS leg |
| --- | --- | --- | --- | --- |
| 0 | 32 | depositor | x-only key of the depositor | same |
| 32 | 1 | kind | 0x01 | 0x00 |
| 33 | 32 | covenantId | covenant_id | zero |
| 65 | 32 | templateHash | template_hash | zero |
| 97 | 8 | prefixLen | template_prefix_len | 0 |
| 105 | 8 | suffixLen | template_suffix_len | 0 |
| 113 | 8 | amount | amount (token units) | amount (sompi) |
| 121 | 1 | deliveryType | owner type (0 PUBKEY, 1 SCRIPT_HASH, 2 COVENANT_ID) | 0 P2PK, 1 P2SH |

Partial absent and partial present map to different states (`lotCount` 1 against at least 2), and every other terms field has one encoding, so the state is injective in the terms and the address commits to every term (principle 1). settlement_mode is not in the state (a script always means Vault).

The script hash, scriptPubKey and address of a v2 vault are made exactly as for v1 (`TEMPLATE.md`, "Script hash, scriptPubKey and address").

### 4.3 Positions

N legs; K of them are KCC-20, and the terms put every KCC-20 leg before every KAS leg (section 5.3), so KCC-20 legs are 0 to K - 1.

| Inputs | Content |
| --- | --- |
| 0 to N - 1 | Vault of leg i at input i: the authorizer of a KCC-20 leg, or the KAS itself for a KAS leg |
| N to N + K - 1 | Escrowed token of KCC-20 leg j at input N + j |
| then | Fee inputs |

| Outputs, final settle | Content |
| --- | --- |
| 0 to N - 1 | Delivery of leg j at output j |
| N to N + K - 1 | Authorizer KAS of KCC-20 leg j home to its depositor at output N + j |
| then | Change |

| Outputs, tranche (I17) | Content |
| --- | --- |
| 0 to N - 1 | Delivery of leg j at output j |
| N to 2N - 1 | Continuation of the vault of leg i at output N + i |
| 2N to 2N + K - 1 | Remainder token of KCC-20 leg j at output 2N + j |
| then | Change |

With N = 2 these are the v1 layouts for KAS cash (K = 1) and KCC-20 cash (K = 2), position for position.

Mixed final and tranche in one transaction. Each vault checks only its own indexes, so the contract accepts a settle in which vault i is final and vault j is a tranche: vault i's authorizer goes home at N + i, vault j continues at N + j, vault j's remainder token sits at 2N + j, and output 2N + i is not checked by any vault (the builder puts change or nothing there; a filler output is valid). This is accepted by design and pinned by engine tests (section 11.2); it arises only when the legs' escrows hold different numbers of lots (section 4.6). The builders refuse to build it (`TX_LEGS_OUT_OF_STEP`) as a convenience for honest parties, not as a safety property.

Same covenant ID across vaults. If two vaults of one trade share one covenant ID (funded in one genesis group), `[C3]` sees two continuations and every tranche fails for both; a final settle and a refund still work. The fund builders therefore emit one genesis group per leg, and the verifier and `TX_LINEAGE` refuse vault UTXOs of one trade with equal covenant IDs.

Refund keeps the v1 layout: the vault UTXO at input 0, its KAS at output 0; for a KCC-20 leg the escrowed token at input 1 and home at output 1.

### 4.4 Entry `settle(sig authSig, int lots)`

Notation: i = legIndex, N = legCount; `amount_j`, `cov_j` and so on are fields of leg record j; `unit_j = amount_j / lotCount` (`OpDiv`); `held` is what this vault's escrow holds; `tranche = lots * unit_i` (`OpMul`); `final` is `tranche == held`; `myCov = OpInputCovenantId(this.activeInputIndex)`; `destSpk(type, id)` is `ScriptPubKeyP2PK(id)` for type 0 and `ScriptPubKeyP2SH(id)` for type 1. The requires, in evaluation order:

| Tag | Require | Purpose |
| --- | --- | --- |
| `[S1]` | `this.activeInputIndex == legIndex` | Fixes this vault's own input position, so every index it computes (N + i, 2N + i) is unambiguous. It does not by itself bind the other vault inputs to the same trade; that is `[S10]` |
| `[V1]` | `legCount <= MAX_LEGS` | The loop bound is checked by the contract, not by the compiler's runtime assertion |
| `[V2]` | `legs.length == legCount * LEG_RECORD` | Every slice of the leg list is inside it |
| `[V5]` | `legIndex >= 0 && legIndex < legCount` | The script bounds its own leg index instead of relying on an out-of-range slice failing |
| `[P1]` | `lots >= 1` | A tranche moves something |
| | KCC-20 leg i: | |
| `[E1]` | `OpCovInputCount(cov_i) == 1` | As v1: the escrow is the only input of its covenant |
| `[E2]` | `OpCovInputIdx(cov_i, 0) == N + i` | The escrow sits at its position |
| (builtin) | `readInputStateWithTemplate(N + i, prefixLen_i, suffixLen_i, templateHash_i)` | The escrow runs the named template and holds the state read |

| `[P3]` | `held % unit_i == 0` | The escrow holds whole lots |

36 tagged requires, 37 with `[S10]`, among them `[F4]` and `[F1]` (below). With `lotCount = 1` (no partial), `[P2]` to `[P4]` and `lots >= 1` hold only for `lots = 1` and `held = amount_i`, which is v1's `[E5]` and `[S2]`; `[P5]` and `[P6]` then hold trivially (`minLot = 1`, remainder 0); `final` always holds and the tranche branch is unreachable. That is how N = 2 reproduces v1 behaviour (section 11.1).

`[S10]`, sibling binding (D44). Without it, a settle may combine vaults of two trades whose delivery tables are identical: every vault present sees its deliveries and passes. Each vault still releases only to its own terms' recipients, so no output goes to anyone the terms do not name, but the economic pairing is not the agreed one. Worked case: trade A (Alice delivers X to Bob, Bob delivers Y to Alice) and trade B (Carol delivers X to Bob, Dave delivers Y to Alice). A settle of A's leg 0 with B's leg 1 pays X to Bob from Alice and Y to Alice from Dave, and leaves A's leg 1 and B's leg 0 live. If both are then refunded, Bob has received X without paying, Dave has paid Y and Carol has paid nothing: a party ends worse off than under either agreed trade. So siblings must be bound. The intended form: for each j other than i, input j runs template v2 (`readInputStateWithTemplate(j, ...)` with this template's hash) and its state equals this vault's with `legIndex = j`. Whether silverscript v1.0.0 can read or rebuild a sibling whose state holds the variable-length `legs` field is not known (`validateOutputState` refuses such a field, section 3.2). I16 probes it first. If it compiles and fits the budget, `[S10]` is part of the template before the freeze. If it does not, I16 records a blocker, the fallback is disclosure (verify and the CLI state that a settle may combine trades with identical delivery tables, and the builder refuses to build one), and the owner decides under D44 before the D30 freeze. No check is weakened to make it fit.

Stray escrows and the stranded real escrow. `final` is computed from whichever escrow the settler places at input N + i, and anyone can send a token owned by the vault's script hash. In the first draft a stray of 1 lot made `final` true below min_lot (`lots >= minLot || final`) and, for a KCC-20 leg, sent the authorizer home while the real escrow stayed behind with no vault UTXO. `[P5]` and `[P6]` close the min_lot bypass: every tranche is at least min_lot lots and no remainder falls below it. A stray of at least min_lot whole lots (or, without partial, of exactly the leg amount, as in v1) can still settle; it costs whoever sent it that many lots, which the agreed recipient receives at the agreed ratio, and it can still strand the real escrow of that leg. Recovery: anyone funds a new authorizer at the vault address (a plain output for terms without partial, a new KIP-20 genesis for partial terms, since consensus runs no script at a genesis); the stranded escrow then settles or is refunded as usual, and the refund builder accepts a plain authorizer for partial terms in this case. The fund and settle builders and the verifier warn (a warning, not a refusal) when the token covenant's UTXOs known to them include more than one owned by a vault's script hash. The key holder's runbook gains the recovery step with I17.

Tranche griefing (D42). `lots` is a witness chosen by whoever submits the settle. On partial terms without an authority, anyone can front-run the parties' intended tranche with another `lots` (at least min_lot, within `[P6]`), paying only the fee and, per KCC-20 leg, a new carrier; the parties' pending transaction is then invalid because its inputs are spent, and the trade can be pushed into many min_lot tranches. No value leaves the agreed recipients. Partial terms with an authority are not exposed, since `[S6]` needs its signature. The CLI and verify warn on partial terms without an authority.

Arithmetic cannot wrap: every product is checked by `OpMul`, which fails the script on overflow, and `OpDiv` fails on a zero `lotCount` (measured, section 3.1). Structure-checked terms never produce either.

### 4.5a Inputs outside the layout

kcc20.sil lets a token owned by a script hash (or a covenant ID) move in any transaction that also spends an input at that address (or of that covenant). A vault that constrained only its own leg's covenant would let a token of another covenant owned by its script hash move with any spend of it (known limitation L20). The vault refuses such spends:

| Tag | Entry | Require | Purpose |
| --- | --- | --- | --- |
| `[F4]` | settle | `tx.inputs.length <= legCount + 18` (`MAX_INPUTS_AFTER_VAULTS`) | The bound of `[F1]`, checked by the contract |
| `[F1]` | settle | every input N + k, k from 0: `kind_k == KCC-20` (an escrow slot, k < N) or `OpInputCovenantId(N + k)` is zero | No token of another covenant rides along |
| `[F5]` | refund | `tx.inputs.length <= 12` (`MAX_INPUTS`) | The bound of `[F3]` |
| `[F3]` | refund | every input from 1 on: `OpInputCovenantId(i)` is zero or, for a KCC-20 leg, `cov_i` | No token of another covenant rides along; `[R8]` and `[R9]` place the leg's own token at input 1 |

`[F1]` does not check the escrow slot N + j of a KCC-20 leg j: vault j is an input of the same settle (`[S10]`), and its `[E1]` and `[E2]` require there the only input of `cov_j`. Nor does it check the vault slots 0 to N - 1, which `[S10]` makes this trade's vaults (a vault UTXO may carry its own covenant, for tranches and partial funding). So the inputs that carry a covenant are exactly the vaults and the escrows. The leg kinds are collected in the delivery loop and padded with 18 KAS kinds, so `kinds[k]` exists for every k the loop reaches.

Consequences: a settle has at most N + 18 inputs (10 escrows and 8 fee inputs at N = 10), a refund at most 12; the builders refuse more (`TX_TOO_MANY_INPUTS`). A token of another covenant sent to a vault cannot move at all. Measured against the template before the check (`docs/evidence/template-fix-2026-10-19/v0.4-template-units.txt`, `tests/engine/v2_foreign_covenant.rs`): the suffix grew from 7,065 to 8,477 bytes; each input after the vaults costs a settle 106 to 107 script units and a refund 167 to 168, which the budgets add for every input the template allows (section 6.4); every vault input of a settle also hashes its siblings' larger scripts for `[S10]` (section 9.2). Engine tests: `tests/engine/v2_foreign_covenant.rs`.

### 4.6 Partial settlement: why the vault continues with unchanged state

The I17 requirement asks for a vault that "continues as the same covenant with the remaining amount and unchanged terms". This design keeps the remaining amount where it already lives, in the escrow (the token's amount, or the KAS value of a KAS leg), and keeps the vault's script unchanged:

- A tranche of `lots` lots delivers `lots * unit_j` of every leg j and returns `held - tranche` of each leg to the same vault (`[C5]`, `[C6]`, the remainder builtin). Remainder plus tranche equals the escrowed amount for every leg, which is the I17 requirement; the continuation keeps every terms field because it is the same script.
- The authorizer (or the KAS of a KAS leg) of a partial trade is funded as a KIP-20 covenant genesis and continues as the same covenant ID (`[C2]` to `[C4]`). The covenant gives each leg a lineage that receipts and the verifier follow across tranches, and it lets every entry forbid an unchecked continuation (`[C1]`, `[R15]`).
- A counter of filled lots in the state is not possible with silverscript v1.0.0 (section 3.2), and it would not add safety: anyone can fund a vault address at any counter value as a new genesis, because consensus runs no script at a genesis.

What each party can rely on, and what it cannot (D34):

- Every tranche exchanges whole lots of every leg at the agreed ratio, because every vault checks every delivery. A party never delivers more from its vault than its escrow holds, and never delivers a lot without receiving the agreed lot of every other leg.
- Quantity is not enforced across tranches. A leg funded with fewer lots than its amount, or a stray escrow of at least min_lot whole lots owned by a vault, can settle; the trade then fills as far as the smallest leg allows and the rest of each leg is refundable. A leg holding fewer than min_lot lots cannot settle at all (`[P5]`) and is refunded. Without `partial_allowed` none of this applies: the escrow must hold exactly the leg amount, as in v1.
- Because quantity is not enforced, every v2 receipt of a partial trade states the quantity settled by that transaction and the cumulative quantity of the lineage against the terms total for every leg, and v2 verify of a partial receipt fails if those fields are missing (`RECEIPT_` code appended by I17 with its `CLI.md` update). The disclosure in this section is part of the specification; README and the demo page carry it when they describe partial settlement (I17), and the WASM SDK returns the same fields, so a third-party tool cannot read a tranche receipt without them.
- Lockstep is not enforced by the contract: legs at different remaining amounts can settle a tranche together, since every slot belongs to exactly one leg, and a final settle of one vault can sit beside a tranche of another (section 4.3, mixed case). The builders refuse it (`TX_LEGS_OUT_OF_STEP`) as a convenience only.
- Each tranche moves every KCC-20 leg's carrier KAS to the delivery (`[D2]`) and needs a new carrier at least as large for the remainder (`[C9]`), paid by the settler from fee inputs. Over T tranches the settler adds T - 1 carriers per KCC-20 leg, which end with the recipients.
- A KCC-20 token whose template allows fewer than two covenant outputs per transfer cannot settle a tranche (the delivery and the remainder are two outputs of its covenant); it can still settle in full. The token's ABI artifact does not state the limit, so the builder cannot check it; the token's own script refuses (as for v1's `maxCovIns`). The fixture tokens allow two (measured, `tests/engine/instantiate.rs`).

### 4.7 Basket operations

A basket of N parties settles only when every leg is funded. A party that never funds leaves the others' escrows waiting; this is the basket form of the free option of R12 (section 10.6). The contract cannot force anyone to fund, so the design limits how long and how badly a missing leg can hold the others:

- Assembler. One party, or a coordinator the parties name, assembles the trade: proposes the terms, collects every leg's verified address, tracks funding and builds the settle. The assembler holds no key and no funds and gains no right in the contract; any party may take over the role, since every step uses public data. Only a party named in the terms (or the authority) can sign a refund.
- Funding window. The terms carry an expiry; the CLI's default expiry for v2 terms is short (D46: 24 hours of DAA at the network's target rate from creation), and it asks for a funding deadline well before expiry (default: half the time to expiry) after which nobody should fund.
- Funding order. All parties fund inside the window, in any order; no party is asked to fund first. Revocable funding (the CLI default for N of 3 or more, D46) lets each depositor take its leg back at any time if another leg never arrives. Earmarked funding locks the depositor's own refund until expiry, so the CLI warns before an earmarked fund that the depositor's leg can only come home early if another named party or the authority sends it.
- Status. `impulse v2 verify` reports per leg: unfunded, funded (with amount and lots), settled in part, spent; and warns before the first fund of a party when other legs are unfunded, naming them.
- Unwind of a missing leg. At the funding deadline with a leg still unfunded: revocable depositors refund their own legs; for earmarked legs, any other named party or the authority sends them home at once (a non-depositor refund always goes home to the depositor, section 4.5); otherwise each depositor refunds at expiry. The key holder's runbook carries the unwind for the I16 owner run.

### 4.8 Finality and wording

Every receipt, verify output and CLI message names which of these states it reports; none says "settled" without one of them:

| State | Meaning |
| --- | --- |
| accepted | The transaction is accepted by a chain block of the node's virtual selected chain. It can still be reorganised out. |
| final | The accepting block is at least the configured finality depth below the virtual (the watcher's policy, D18: 600 DAA, changed by the owner on 2026-10-12 from 36,000); this is the depth the operator chose, not a guarantee of the network. |
| counterpart-final | Hashlock only: the counterpart claim or lock is at the counterpart chain's finalized commitment as its source reports it. |

What each flow promises:

- Basket and partial settlement (template v2) are atomic only within one Kaspa transaction: every leg of that transaction moves or none does. A partial trade is a sequence of such transactions; the trade as a whole is not atomic, and each tranche is reported separately.
- Hashlock settlement is two transactions on two chains. It is conditional exchange with residual risk (section 10.6, R2, R9, R10, R12), not atomic settlement. A hashlock trade is reported complete only when the Kaspa claim is final and the counterpart claim is counterpart-final.
- Unqualified "atomic" and "atomic DvP" are not used for hashlock (I18), and neither is any word the existing unverifiable-claim screen refuses (`RELEASE_UNVERIFIED_CLAIM`, which already lists the "trust" adjectives), anywhere: docs, README, receipts, CLI or SDK strings. A grep test in CI (section 11.1) fails on those words in any file or string of the hashlock code and docs, and on "settled" in a receipt or CLI string that does not name a state from the table above.

### 5.2 Layout

Conventions are v1's (`ENCODING.md`, "Conventions"): fixed-width little-endian unsigned integers, 32-byte arrays as they are, presence byte for optionals, kind byte for variants, no padding, nothing after the last field. Terms v2 hold no variable-length byte string.

| # | Field | Encoding | Bytes |
| --- | --- | --- | --- |
| 1 | version | u8, `0x02` | 1 |
| 2 | network | u8: `0x00` mainnet, `0x01` testnet | 1 |
| 3 | nonce | u64 | 8 |
| 4 | authority_key | optional 32-byte x-only key | 1 or 33 |
| 5 | leg_count | u8 | 1 |
| 6 | legs | leg_count times Leg v2 | 107 or 179 each |
| 7 | earliest_daa | optional u64 | 1 or 9 |
| 8 | expiry_daa | u64 | 8 |
| 9 | funding_mode | u8: `0x00` revocable, `0x01` earmarked | 1 |
| 10 | partial | optional: lot_count u64, then min_lot u64 (present means `partial_allowed`) | 1 or 17 |
| 11 | trade_ref | 32 bytes | 32 |

**Leg v2**, in this order:

| Field | Encoding | Bytes |
| --- | --- | --- |
| depositor_key | 32-byte x-only key | 32 |
| asset | v1's Leg encoding: kind byte then the kind's fields then amount (`0x00` KAS: amount u64; `0x01` KCC-20: covenant_id 32, template_hash 32, template_prefix_len u32, template_suffix_len u32, amount u64; `0x02` external: amount u64) | 9 or 81 |
| delivery | Destination v2 | 33 |
| refund | Destination v2 | 33 |

**Destination v2**: identifier_type u8 then identifier 32. For a KCC-20 leg it is a KCC-20 owner (`0x00` PUBKEY, `0x01` SCRIPT_HASH, `0x02` COVENANT_ID, as kcc20.sil). For a KAS leg, `0x00` is a Schnorr P2PK with that x-only key and `0x01` a P2SH with that script hash; there is no ECDSA form in v2 (D35). An identifier_type above `0x02` is `TERMS_INVALID_TAG` at decode.

There is no settlement_mode byte: terms v2 describe vault trades only. Direct mode, external cash and KAS destinations of the P2PK-ECDSA class stay v1 features (D35).

Decoding refuses, first failure returned: a version byte other than `0x02` (`TERMS_V2_VERSION`, before anything else), input that ends inside a field (`TERMS_TRUNCATED`), an unknown kind or type byte (`TERMS_INVALID_TAG`), a presence byte other than 0 or 1 (`TERMS_INVALID_PRESENCE`), bytes after trade_ref (`TERMS_TRAILING_BYTES`). `decode(encode(t)) = t` and `encode(decode(b)) = b`. A dispatcher `terms::decode_any` reads the version byte and calls the v1 or v2 decoder; any other version byte is `TERMS_VERSION_UNKNOWN`.

### 5.3 Validation

Structure checks, time-independent, in this order, first failure returned. `TermsV2::validate_structure` is the only way to obtain `ValidatedTermsV2`.

1. version 2: `TERMS_V2_VERSION`.
2. leg_count from 2 to MAX_LEGS: `TERMS_LEG_COUNT`.
3. Each depositor key in leg order, then authority_key: valid BIP-340 x-only keys, `TERMS_INVALID_KEY`.
4. At least two distinct depositor keys: `TERMS_LEGS_ONE_PARTY`. Then authority_key, if present, differs from every depositor key: `TERMS_AUTHORITY_IS_DEPOSITOR`.
5. Each leg is KAS or KCC-20: `TERMS_LEG_KIND`. Every KCC-20 leg comes before every KAS leg: `TERMS_LEG_ORDER`.
6. Each leg in order: amount above zero (`TERMS_AMOUNT_ZERO`); at most `MAX_SOMPI` for KAS and `i64::MAX` for KCC-20 (`TERMS_AMOUNT_OUT_OF_RANGE`); for KCC-20, covenant_id then template_hash not all zero (`TERMS_ZERO_IDENTIFIER`), and the template lengths as v1 (`TERMS_TEMPLATE_LENGTH`). Then the KCC-20 covenant IDs are pairwise distinct (`TERMS_LEGS_SAME_COVENANT`).
7. Each leg's delivery then refund: a KAS leg's type is `0x00` or `0x01` (`TERMS_DESTINATION_KIND`); every identifier not all zero (`TERMS_ZERO_IDENTIFIER`); a PUBKEY identifier, and a KAS P2PK key, a valid x-only key (`TERMS_INVALID_KEY`).
8. expiry_daa then earliest_daa below 500,000,000,000 (`TERMS_EXPIRY_NOT_DAA`, `TERMS_EARLIEST_NOT_DAA`); earliest_daa present and zero (`TERMS_EARLIEST_ZERO`) or above expiry_daa (`TERMS_EARLIEST_AFTER_EXPIRY`).
9. Partial, if present: lot_count at least 2 and min_lot from 1 to lot_count (`TERMS_PARTIAL_LOTS`); every leg amount a multiple of lot_count (`TERMS_PARTIAL_INDIVISIBLE`).

Creation checks are v1's, unchanged in order and codes (`TERMS_NETWORK_MISMATCH`, `TERMS_EXPIRY_NOT_AFTER_CREATION`, `TERMS_EXPIRY_BEYOND_HORIZON`).

Why the new checks:

- Distinct covenants: `[E1]` makes each escrow the only input of its covenant, so two legs of one token would never settle. Terms v2 therefore carry each KCC-20 token at most once; parties who would move one token in several lines (or in both directions) combine them into one leg before agreeing the terms. Impulse does not do that combination for them.
- KCC-20 legs first: escrows and authorizer returns then sit at contiguous positions with no gaps (section 4.3). The contract does not depend on it.
- Authority distinct from every depositor: the contract tells roles apart by key (`[R3]`), as in v1.
- lot_count at least 2: partial with one lot is the same trade as no partial, and the state must have one encoding per terms value.

## 6. Transactions v2

The builders live in `impulse_core::v2::tx`, take `ValidatedTermsV2` only, hold no key, and return an unsigned IPST of version 2 (`IPST.md` with `"ipst": 2` and the terms v2 bytes in place of the v1 terms). Common form, fee inputs, signature slots and lock time are v1's (`TRANSACTIONS.md`) except where stated.

### 6.1 Shapes

| Transaction | Inputs | Outputs | Lock time |
| --- | --- | --- | --- |
| fund KCC-20 leg | depositor's token inputs (leader, delegates), payer P2PK inputs | 0 escrow: exactly amount_i, owner SCRIPT_HASH of vault i, not a minter; 1 authorizer at vault i; then token change, KAS change | 0 |
| fund KAS leg | payer P2PK inputs | 0 exactly amount_i at vault i; change | 0 |
| settle, final | section 4.3; vaults `settle(authSig, lots)`; each escrow a `transfer` leader with witness = its vault input | section 4.3, final | earliest_daa or 0 |
| settle, tranche (I17) | as final | section 4.3, tranche; each continuation bound to its vault input as a continuation of the vault's covenant; each escrow's new states are the delivery and the remainder, in output order | earliest_daa or 0 |
| refund | v1 refund layout, `refund(s, signerLeg)` | v1 refund layout | expiry_daa for an earmarked depositor's own refund, else 0 |

With `partial_allowed`, the fund builders make the authorizer (KCC-20 leg) or the KAS output (KAS leg) a KIP-20 genesis: covenant binding `(covenant_id(outpoint of the first payer input, [that output]), authorizing_input = the first payer input)`. Each leg is funded in its own transaction with its own genesis group, so no two vaults of one trade share a covenant ID (section 4.3). Without it they make plain outputs, as v1. The escrowed token is never a covenant of the vault; it stays a token of its own covenant owned by the vault's script hash, as in v1.

### 6.2 Mass caps and minimum KAS (D29, D37)

v2 transactions are larger than v1's (section 9), so the v2 builders check each mass dimension against its own cap, `TX_V2_MASS` above any of them. The caps are not hard-coded: each is read from the pinned `Params::block_mass_limits().after()` of the configured network and reduced by a reserve, so that a v2 transaction never fills a dimension of a block alone (section 3.1, measured, source). With the D37 default reserve of 10 percent:

| Dimension | Pinned block limit after Toccata (measured, source) | CAP_V2 (D37) |
| --- | --- | --- |
| compute | 500,000 | `CAP_V2_COMPUTE` = 450,000 |
| storage | 500,000 | `CAP_V2_STORAGE` = 450,000 |
| transient | 1,000,000 | `CAP_V2_TRANSIENT` = 900,000 |

A unit test reads the pinned `Params` for mainnet and TN10 and asserts these values, so a change in the pin cannot change a cap silently. v1 keeps its 100,000 for every dimension. Until 30 minutes before Toccata activation the pinned mempool applies 100,000 per dimension as a standardness rule (section 3.1); a node in that state, or a wallet that still applies 100,000, does not relay a v2 settle above 100,000 in any dimension, which is most settles above N = 2 (modelled, section 9). The CLI warns when the transaction exceeds 100,000 in any dimension.

Minimum KAS per created or chosen output, by the v1 reasoning (`TRANSACTIONS.md`, "Minimum KAS per leg") with the v2 cap and the v2 output count:

```
MIN_V2(p, O) = ceil(p^2 * 10^12 * O / CAP_V2)
O = N + K + 1 for terms without partial, 2N + K + 1 with partial
```

with `CAP_V2 = CAP_V2_STORAGE` in this formula. p is the plurality (1 for a KAS output, 2 for a KCC-20 token). Every v2 output that the builder creates or tops up must hold at least `MIN_V2(p, O)`, which bounds the storage mass of the largest transaction the leg takes part in by CAP_V2_STORAGE. That includes each KAS leg's delivery `lots * unit_j`, which cannot be topped up (`[S5]`): the fund builder refuses a KAS leg whose `unit` is below `MIN_V2(1, O)` (`TX_BELOW_MIN_KAS`). This is a modelled upper bound; the builder still computes the exact storage mass with the pinned calculator before it returns. D97: for partial terms a vault output holds at least MIN_V2(2, O) (`min_vault_v2`), because a vault output of a partial leg carries a covenant ID and occupies two storage units; this covers the genesis output of a partial funding, every tranche continuation and the KCC-20 authorizer output, and `TX_BELOW_MIN_KAS` is raised below it. Without partial the floor stays MIN_V2(1, O). The contract does not enforce the minimum: a hand-funded KAS leg, or a stray of small lots, can leave a vault whose tranche or settle exceeds the storage cap and cannot be mined, while its refund still works. The verifier flags (a warning) any vault UTXO whose unit is below `MIN_V2(1, O)` for a KAS leg or whose carrier is below `MIN_V2(2, O)` for a KCC-20 leg.

### 6.3 Builder refusals added in v2

Beyond the v1 refusals that keep their meaning (`TX_EXPIRED`, `TX_ESCROW_MISMATCH`, `TX_LEG_AMOUNT`, `TX_TOKEN_TEMPLATE`, `TX_TOKEN_INPUT`, `TX_KAS_INPUT`, `TX_DUPLICATE_INPUT`, `TX_INSUFFICIENT_FUNDS`, `TX_BELOW_MIN_KAS`, `TX_FEE_TOO_LOW`, `TX_NONSTANDARD_CHANGE`, `TX_SIGNATURE`, `TX_SIGNATURE_SLOT`, `TX_ENCODING`, `TX_UTXO_VALUE`), in order: the vault inputs (`TX_V2_NOT_AT_VAULT`: not at its vault's scriptPubKey, or a covenant where the terms have no partial), one vault and, for KCC-20, one escrow per leg (`TX_LEGS`), the tranche (`TX_TRANCHE`), the lineage (`TX_LINEAGE`), lockstep (`TX_LEGS_OUT_OF_STEP`), then the shared checks with `TX_V2_MASS` in place of `TX_MASS`. A refusal from the terms or the template keeps its own code. Exact order (fixed by I16, `impulse_core::v2`): settle: `TX_EXPIRED`; each offered leg's vault UTXO in leg order (`TX_V2_NOT_AT_VAULT`); one vault per leg and one escrow per KCC-20 leg (`TX_LEGS`); each KCC-20 escrow in leg order (`TX_TOKEN_TEMPLATE`, `TX_ESCROW_MISMATCH`); each leg's amount in leg order (`TX_LEG_AMOUNT` without partial, `TX_TRANCHE` with it); `TX_LINEAGE`; `TX_LEGS_OUT_OF_STEP`; then the shared checks. Refund: the leg index (`TEMPLATE_V2_LEG_INDEX`); the signer (`TX_REFUND_SIGNER`); the vault UTXO (`TX_V2_NOT_AT_VAULT`); the escrow (`TX_WRONG_MODE` for a KAS leg, `TX_REFUND_SIGNER` when anyone but the depositor offers none, `TX_TOKEN_TEMPLATE`, `TX_ESCROW_MISMATCH`, `TX_LEG_AMOUNT` when anyone but the depositor offers other than whole lots of at most the leg amount); then the shared checks. Fund: `TX_VAULT_MISMATCH`; `TX_WRONG_MODE` (leg kind; partial terms, whose genesis funding is I17's); `TX_EXPIRED`; then v1's fund checks with MIN_V2 minimums (`TX_BELOW_MIN_KAS`); then the shared checks. The shared checks, in v1's order: `TX_KAS_INPUT`, `TX_DUPLICATE_INPUT`, `TX_UTXO_VALUE`, `TX_NONSTANDARD_CHANGE`, `TX_INSUFFICIENT_FUNDS`, `TX_BELOW_MIN_KAS` (change below MIN_V2(1, O)), `TX_V2_MASS` (compute, transient, storage), `TX_FEE_TOO_LOW`.

### 6.4 Budgets

Each input's compute budget is sized as v1 sizes it, from the measured rules of section 9.2 (`SETTLE_RULE` and the refund rule in `tests/engine/v2_measure.rs`, raw data in `docs/measurements/v2-max-n.txt`) plus a margin of 10,000 units and 2 percent (D56 point 4). The rule adds the cost of every input `[F1]` or `[F3]` may check (section 4.5a). A settle has at most N + 18 inputs and a refund at most 12 (`TX_TOO_MANY_INPUTS`, checked after the fee inputs). Template v2 is not frozen until the measured table and fitted rule are committed (section 4.1, D30).

Points sections 5 to 8 left open, decided in I16 (D56, defaults applied): (1) the v0.2 codes are exported as their own lists (`impulse_core::v2::{TERMS_V2_ERROR_CODES, TEMPLATE_V2_ERROR_CODES, TX_V2_ERROR_CODES, VERIFY_V2_ERROR_CODES}`), so the v1 lists and the SDK's v1 code lists stay unchanged; (2) the v2 verifier reuses v1 `VERIFY_` codes in their v1 meaning and adds only the three of 8.4; (3) the fund builders refuse partial terms (`TX_WRONG_MODE`), because section 6.1 funds them as a KIP-20 genesis, which is I17's builder, and the settle builder accepts partial terms and builds the final settle of what the escrows hold (whole lots, same count, at least min_lot), refusing faults with `TX_TRANCHE`, `TX_LINEAGE` and `TX_LEGS_OUT_OF_STEP`, tranches being I17's; (4) budgets as above; (5) settle tops up authorizer-home and token-carrier outputs to MIN_V2, and never tops up KAS deliveries or refund output 0; (6) a refund by anyone but the depositor takes whole lots of at most the leg amount (exactly the amount without partial), `TX_LEG_AMOUNT` otherwise; (7) a third vector set, `tests/vectors/ipst_v2/`, beside `terms_v2/` and `vaults_v2/`; (8) the ten-leg vector is named "ten-leg-bilateral"; (9) gitleaks allowlists the public `depositor_key` field of `tests/vectors/terms_v2/*.json`.

### 6.5 Command line, watcher and SDK (I16 CLI step)

Fixed before the code (D57). The v2 commands are a separate command group, `impulse v2`, in `crates/impulse-cli/src/v2_cmd.rs`; the v1 commands, their files and their codes do not change, and each version refuses the other's files with the codes it already has (a v1 command reads a v2 terms file as `CLI_TERMS_JSON` and a v2 IPST as `IPST_UNSUPPORTED_VERSION`; a v2 command reads a v1 terms file as `CLI_TERMS_JSON` and a v1 IPST as `IPST_UNSUPPORTED_VERSION`). Everything `spec/CLI.md` fixes for v1 holds for `impulse v2` unless this section says otherwise: the network selection (testnet unless `--network mainnet`), the node and its transport rule, the key file and the one signing module, the common builder arguments, the transaction lines, "prints nothing until every check has passed", and the codes. No `CLI_` code is added.

**Terms draft and terms file v2.** A terms file v2 is a JSON object with exactly `terms` (the JSON form of section 5.4), `canonical` and `terms_hash`, read as `spec/CLI.md` reads a v1 terms file (`CLI_TERMS_JSON`, `CLI_TERMS_FILE_INCONSISTENT`), and refused unless `terms.version` is 2 (`CLI_TERMS_JSON`). A draft is that JSON form with three keys that may be absent or `null`: `nonce` (drawn from the operating system's random source), `expiry_daa` (the D46 default, the creation DAA score plus 864,000, 24 hours at the nominal 10 DAA scores per second), and `funding_mode` (revocable, D46, for 3 legs or more; for 2 legs it must be given, `CLI_TERMS_JSON`).

**Party check.** v2 has no buyer and seller: the parties are the depositors. `--my-key` (an x-only public key; never a private key) must be the depositor of at least one leg (`CLI_ROLE_KEY_MISMATCH`). Then, with `CLI_DESTINATION_NOT_MINE` for any failure: (1) the refund destination of each leg `--my-key` deposits pays `--my-key` (a KAS P2PK of that key, or a KCC-20 PUBKEY owner of it) or equals a `--my-refund` pin, and never pays another depositor's key or the authority key; (2) at least one leg that `--my-key` does not deposit is delivered to it: its delivery pays `--my-key` or equals a `--my-delivery` pin. Pins are written as in `spec/CLI.md` (a Kaspa address of the network, or `kcc20:<type>:<hex>`) and may be repeated (`CLI_DESTINATION_PIN_INVALID` for a pin that does not parse or names another network); a KAS pin stands for the version-0 script of its address. The output names, per leg, its depositor and whether it is the user's, and for each of the user's refunds and each delivery to the user whether it pays `--my-key` or equals a pin. The summary shows every leg (depositor, kind, token, amount, delivery, refund, each destination marked with the depositor key or authority key it pays, or as a script to check), the authority, `earliest_daa`, `expiry_daa` with the time left, the funding deadline (D46: half the time from the creation or current DAA score to expiry), the funding mode, and `partial`.

**Before funding.** `v2 terms new`, `v2 address`, `v2 fund build` and `v2 ipst sign` of a funding refuse terms with a KAS leg whose unit is below MIN_V2(1, O) (`TX_BELOW_MIN_KAS`, the fund builder's own refusal of section 6.2, raised earlier) and with a KCC-20 template that is not a pinned kcc20.sil build (`CLI_TEMPLATE_UNPINNED`). `v2 terms new` prints a `warning:` line for an unpinned template instead.

**Value cap.** As `spec/CLI.md`, "Value cap", with the trade value of v2 terms: the larger of `--kas-equivalent` (the KAS value of all legs together) and the sum of the KAS legs. A KCC-20 leg makes the declaration required (`CLI_VALUE_UNKNOWN`). The sum, not the largest leg, because a v2 trade escrows every leg at once (D57).

## 7. Verify and decode v2

`impulse_core::v2::verify` mirrors `VERIFY.md` for N legs: before funding, every leg's address is offered (`VERIFY_ADDRESS_MISSING`), parses (`VERIFY_ADDRESS_MALFORMED`), carries the terms' network (`VERIFY_ADDRESS_NETWORK`), and pays this leg's vault; an address of another leg's vault is `VERIFY_V2_WRONG_LEG`, anything else `VERIFY_V2_ADDRESS_MISMATCH`. After a spend, a revealed script must be the v2 template (`VERIFY_V2_TEMPLATE_MISMATCH`) and decode to the agreed terms and leg (`TEMPLATE_V2_*`, `TERMS_*`). A tranche continuation is the same script as the vault it continues, so it verifies as that vault; its lineage is checked from the covenant ID of the spent vault input. The v1 decoder does not decode v2 spends (they are not v1 vaults); a v2 decoder, if I16 or I17 needs one for receipts, appends its codes to `DECODE_` with a spec update.

v2 verify also: refuses vault UTXOs of one trade with equal covenant IDs (`TX_LINEAGE`, section 4.3); reports each leg's funding status (section 4.7); names the finality state of anything it reports (section 4.8); and prints these warnings, which never change its exit status: more than one token UTXO owned by one vault's script hash (section 4.4, strays); partial terms without an authority (tranche griefing, section 4.4); a vault UTXO below the minimum of section 6.2; a settle that would exceed 100,000 grams in any dimension (section 6.2); and, while `[S10]` is not in the template, that a settle may combine trades with identical delivery tables (D44).

The settle carries N vault scripts, each the full template plus the full state, so its size grows with N times (template + state). A modelled estimate from the probe, labelled modelled and not for publication: per vault input about `T + 142 + 187N + 120` bytes with T about 8,650 bytes at MAX_LEGS 10 (the probe's 7,643 plus about 1,000 for the refund token logic), and per escrow input about `T_tok + 200` bytes, where T_tok is the token template (about 1,700 bytes for the fixture tokens, up to about 6,100 bytes for the padded variants of section 9.2). Every output is P2SH (section 3.1), so the output-scriptPubKey term of compute mass is `10 * 37 = 370` grams per output, about `370 * (2N + K + 1)` at most; the token templates cost through the escrow inputs' size, not through the outputs.

Per dimension, for N KCC-20 legs with fixture tokens (modelled):

- Transient (4 per byte): roughly 89,000 grams at N = 2, 136,000 at N = 3, 447,000 at N = 9 and 504,000 at N = 10, all under CAP_V2_TRANSIENT (900,000). The first draft compared 504,000 with a single 500,000 cap; transient has its own limit of 1,000,000 (section 3.1).
- Compute (1 per byte, plus the output term, plus 100 per budget unit): the size term is a quarter of the transient figure (about 126,000 grams at N = 10) and the output term at most about 11,000; the budget term is unknown until I16 measures units. Each of the N vaults validates all N deliveries, hashing each token template once per vault, so total units grow with N squared (section 9.2). Compute is the dimension most likely to bind, and the only one this model cannot bound yet.
- Storage: bounded by the MIN_V2 rule (section 6.2), exact at build.

So, if the model holds: under 100,000 grams in every dimension v2 settles only N = 2; under CAP_V2 the binding dimension and the practical maximum are unknown until the budget term is measured. These figures decide nothing on their own and are not published. I16 measures them per dimension (section 9.3). If N_max(CAP_V2) is below 10, D38's default lowers MAX_LEGS to the measured N_max before the D30 freeze, and the N = 10 tests move to the lowered MAX_LEGS. If MAX_LEGS stays 10 and N = 10 validates in the engine but exceeds a cap, N = 10 is an engine-only test, never a product claim. The levers I16 may use without weakening a check: hoist the record offset out of each field read, and re-measure; or lower MAX_LEGS under D38. Raising a cap above the pinned limit less its reserve is not a lever.

### 9.2 Script-unit budget method

As v1 (`TRANSACTIONS.md`, "Compute budgets"): units are measured, not assumed, with kcc20.sil padded to three template lengths (the fixture, about 3,800 and about 6,100 bytes) and N in {2, 3, 5, 10}, for the settle of every leg kind, final and tranche, with and without an authority, and for each refund role. The test `v2_measure::per_byte_and_per_leg_units_are_measured` fits and asserts the rule below.

Measurement (I16, D49) showed that the form first specified here (a `B * N` term, no `N^2`, `K` or per-input terms) does not hold for template v2, and the rule below is the one committed. The `[S10]` check rebuilds each sibling's redeem script from the vault's own and hashes it, the script grows with N, and the engine charges every pushed byte, so the per-vault units carry an N^2 term as well as the B * N term; KAS legs and KCC-20 legs carry different constants; a tranche settle adds terms of its own. The committed rule has twelve integer coefficients, with `K` the number of KCC-20 legs, `tok_i` 1 when leg i is KCC-20 and 0 otherwise, `tranche` 1 for a tranche settle, `S` the sum of `T_j` over KCC-20 legs:

```
units(settle, vault i) = SIG * hasAuthority + A + B * N + C * N^2 + D * K + E * tok_i
                         + r * T_i + v * S
                         + tranche * (F + G * tok_i + t * T_i + H * N)
```

The values are in `tests/engine/v2_measure.rs` (`SETTLE_RULE`), measured with one fee input: SIG 100,098, A -13,579, B 45,585, C 1,311, D 2,210, E 1,380, r 7, v 10, F 159, G 770, t 10, H 7. The larger B is `[S10]` hashing the siblings' longer scripts. A budget adds 107 units for each input after the vaults the template allows beyond the K escrows and one fee input (`[F1]`, section 4.5a), and a refund budget 168 for each input beyond its own, its token and one fee input. The refund rule is `refund_units_are_measured` in the same file. The fit is over 189 settle points; the integer coefficients differ from a measured point by at most 32 units (largest least-squares residual 13), within the tolerance below. The builder budgets every vault input from the rule plus a margin of 10,000 units and 2 percent (D56 point 4), so a destination form or owner type the fit did not sample is covered. The `r + v = 17` and `v = 10` per byte of v1 hold for v2 (r 7, v 10).

The `v * S` term is per vault input and the `C * N^2` term is per vault input too; the transaction has N vault inputs, so the transaction's total units, and with them the budget part of compute mass, grow with N cubed from the `C` term and with N squared from the `v * N * S` term (for equal templates). The test also fits and asserts the total, the sum of the rule over the N vault inputs:

```
units(settle, all vaults) = N * (SIG * hasAuthority + A + B * N + C * N^2 + D * K)
                            + E * K + (r + v * N) * S
                            + tranche * (N * F + G * K + t * S + H * N^2)
```

The test fails when any measured point differs from the committed rule by more than 1 percent of the measurement or 2,000 units, whichever is larger. A residual above that means the form is wrong and the rule is not committed. The KCC-20 `transfer` rules of v1 hold unchanged for a final settle; the tranche leader validates two outputs and is measured in the same test.

### 10.5 Counterpart HTLC flow (D32: the seller holds the secret)

The Kaspa vault is the first and longer lock; the counterpart HTLC is the second and shorter.

1. Agree the hashlock terms. The seller's CLI makes a fresh 32-byte secret for every trade from the operating system's random source, writes it only to a file the seller names (mode 0600), never prints, logs or transmits it, and puts its sha256 in hash_lock. It never accepts a secret or hash_lock from outside, and refuses a hash_lock already seen in a hashlock vault known to the installation (`XCHAIN_HASH_REUSED`); `xchain verify` refuses the same for the buyer when it finds the hash_lock in another vault. The guarantees of this section hold only when each trade has a fresh secret.
2. The seller funds the Kaspa hashlock vault (escrow and authorizer, as v1's `fund_kcc20`). It is earmarked: the seller cannot take it back before expiry_daa.
3. The buyer verifies the vault address from the terms, then verifies the funding transaction on chain and waits for it to reach its finality depth (D18: 600 DAA, the watcher's policy): exactly one output holds the escrowed token (the asset's covenant ID and template, owned by the vault's script hash, exactly the amount, not a minter), an authorizer pays the vault's address, both are unspent (`impulse_core::htlc::verify_funding`, `HTLC_FUNDING`; `impulse xchain verify-funding`). A transaction ID alone proves nothing: an empty, short or wrongly owned escrow would let the seller take the counterpart amount while the buyer's Kaspa claim fails.
4. Only once step 3 passes, the buyer locks the counterpart amount in the counterpart HTLC with hash_lock, recipient the seller's account, refund the buyer's, timeout T_C.
5. The seller verifies that HTLC on its chain against the counterpart record at finalized commitment: program, asset, amount, recipient, refund, hash, timeout, funded (`impulse xchain verify-counterpart`, `XCHAIN_COUNTERPART_MISMATCH`, `XCHAIN_NOT_FINAL`). Only then does it claim, revealing the secret, at least Δ_claim before T_C. The seller's CLI treats the claim as done only when it is counterpart-final (section 4.8), not when it is submitted; until then it resubmits and reports `XCHAIN_NOT_FINAL`.
6. The buyer, or anyone, reads the secret from the counterpart claim and submits `settleWithPreimage` on Kaspa before expiry_daa (`impulse xchain watch`, then `claim`).
7. If the seller never claims: the buyer refunds the counterpart after T_C; the seller refunds the asset after expiry_daa (or the buyer sends it home at any time with a counterparty refund).

Margin rule, checked at creation (`HTLC_TIMEOUT_MARGIN`) and before the seller's counterpart claim (`XCHAIN_MARGIN_TOO_SHORT`): the wall-clock time at which expiry_daa is reached must be at least T_C plus Δ, where expiry_daa's wall-clock time is estimated, early on purpose, as now plus (expiry_daa minus the current virtual DAA score) divided by `DAA_RATE_MAX`. The estimate is not a guarantee, and user documentation says so.

- `DAA_RATE_MAX` (D45, refines D32). On mainnet it comes from a recorded sample file: the virtual DAA score against wall-clock time on a public node, read only, taken by `scripts/sample-daa.sh` (read only), over at least 7 days. `DAA_RATE_MAX` is 1.5 times the highest rate over any 10-minute window of the sample, and never below the network's target rate (10 per second at 10 blocks per second). A sample whose mean rate over its whole span is below half the target rate is refused (`HTLC_DAA_SAMPLE`). The sample is read from a public node and could be wrong or forged; a slow one would lower `DAA_RATE_MAX` and make the expiry estimate late, the direction in which the buyer loses (R2), so both rules fail safe: the floor keeps the estimate at least as early as the target rate gives, and the mean check refuses a series that is not a live network at that rate. Half is a conservative bound, not a measured one: a fast forged sample only makes the estimate earlier, which is safe; the claim-side time-left advice keeps its pinned 2 times target rate and never blocks on the sample (security review, 2026-10-18, a fail-safe refinement of D45). Until such a file exists the value is 2 times the target rate (20 per second at 10 blocks per second) for TN10 and devnet use, and mainnet creation is refused (`HTLC_DAA_SAMPLE`); a sample older than 30 days, or taken at another blocks-per-second, is also refused. 11 per second, the first draft's figure, was modelled and is withdrawn.
- Why a wide factor: a hashrate surge or a lag in difficulty adjustment can push the DAA rate above target for a while, so expiry arrives earlier in wall-clock time than a tight margin assumes; the lock time is checked against the accepting block's DAA score, which can be ahead of the virtual score read at creation; and a change of blocks-per-second shifts the rate. The CLI refuses to build when the node reports another blocks-per-second than the configured network's (`XCHAIN_NODE_BPS`).
- Δ (D32, D45) is at least the sum of: the DAA equivalent of the D18 finality depth at `DAA_RATE_MAX`, the time the buyer needs to see the reveal at counterpart-final, and a retry window for the Kaspa claim (default 30 minutes); and never less than one hour.
- Δ_claim, the seller's claim lead before T_C, is at least two hours and at least ten times the counterpart chain's time to finalized commitment as its source reports it (D39); the CLI refuses to prepare a claim later (`XCHAIN_MARGIN_TOO_SHORT`).

Requirements on any counterpart HTLC (Solana or another chain), checked before a program is accepted (D33):

- sha256 hashlock over a preimage of exactly 32 bytes (refusing any other length);
- the claim pays a recipient fixed at lock time, and refuses at or after the timeout (an upper-bounded claim);
- the refund pays a refund account fixed at lock time and opens only at or after the timeout;
- the secret appears in the claim transaction or an event readable from a public node;
- published source, a licence compatible with Apache-2.0, and a public review report for any mainnet use.

Mainnet use of the hashlock flow (D39, D40). The mainnet gate is lifted by the owner's answers: D39 (b), mainnet under the value cap with race R2 disclosed, and D40 (the owner, 2026-10-11, confirmed in chat 2026-10-15). On mainnet the per-trade value cap of `spec/CLI.md` applies (`CLI_VALUE_CAP_EXCEEDED` above it, lifted only by `--i-accept-the-risk`), and every `impulse xchain` command on mainnet prints the race R2 disclosure on stderr. R2 is not resolved: it is disclosed. The rules below remain:

- Race R2 is disclosed, not removed: a buyer who controls or colludes with a counterpart block producer or relay can delay the seller's counterpart claim past T_C. No claim-inclusion guarantee is identified in this design. The seller claims early (Δ_claim), and the trade is a conditional exchange across two chains, not atomic settlement.
- The core no longer refuses mainnet: `HtlcVault::instantiate_for_creation`, `verify_address` and `fund` accept mainnet terms, and the command line no longer refuses mainnet for any `xchain` command. `HTLC_MAINNET_GATED` and `XCHAIN_MAINNET_GATED` are reserved, keep their numbers and are no longer returned.
- No counterpart example program is referenced from any mainnet runbook entry, README section or CLI default. A counterpart example program, if one is written, lives under `examples/`, is marked "example, devnet only, not for value" in its README and source header, and is never Impulse-branded as a product. Impulse names no counterpart program: the key holder uses a counterpart program and mainnet they have reviewed themselves, and records both transaction IDs (D40).
- Impulse holds no funds on any chain and runs no service: the counterpart program holds the buyer's funds under its own rules. README and the key holder's runbook carry, with I18, a statement that Impulse is non-custodial software, gives no financial, legal or investment advice, and issues no asset; that any stablecoin named in an example (USDC included) is issued by its issuer under the issuer's own terms, which may include freezing and sanctions controls Impulse cannot see or override; and that users are responsible for their own sanctions and regulatory compliance.
- `claim.rs` (D25) and anything derived from it stay out of `release/v0.2` until D25 records its origin and licence; the maintainers check this before each merge into `release/v0.2`.

No Solana program is chosen in this draft: none has been verified against these criteria in this session. The file `claim.rs` of an earlier work branch (an Anchor HTLC claim module with no recorded origin or licence, D25) is not a candidate until its source and licence are recorded.

### 10.6 Secret-reveal race analysis

| # | Case | Who is at risk | Resolution |
| --- | --- | --- | --- |
| R1 | The seller claims on the counterpart chain at the last moment before T_C | Buyer | The buyer still has at least Δ before expiry_daa by the margin rule, and the counterpart claim cannot land after T_C (requirement above) |
| R2 | The seller's counterpart claim is seen (mempool or leader forwarding), revealing the secret, but does not land before T_C | Seller | The buyer can refund the counterpart and claim the asset, so the seller loses both legs. A buyer who is, or colludes with, a block producer or relay of the counterpart chain can see the claim and delay or censor it past T_C on purpose; claiming early does not remove that attack. Open, not resolved: mitigations (Δ_claim of section 10.5, the claim treated as done only at counterpart-final, resubmission, `XCHAIN_MARGIN_TOO_SHORT`) narrow the window only. Disclosed, not solved: mainnet runs under the per-trade value cap with the R2 notice (D39 b, section 10.5) |
| R3 | A counterpart HTLC whose claim is not bounded by T_C | Buyer | The seller could claim long after T_C and leave the buyer less than Δ. Refused by the requirement above; if the owner ever accepts such a program, the buyer must refund promptly at T_C |
| R4 | The Kaspa claim has no upper bound | Seller, only after expiry | After expiry_daa the seller may refund and the buyer may still claim; the seller's refund is the seller's right once the buyer let Δ pass. Not exploitable before expiry, because the vault is earmarked. `impulse xchain claim` never blocks on the DAA sample or the value cap: the time left is advice only, so a claim after the seller revealed is always buildable (a missing, unreadable, stale or short sample falls back to the pinned worst case with a `warning:` line), and creation and `verify` keep the strict sample rule |
| R5 | A revocable Kaspa vault | Buyer | The seller would see the buyer's claim and race it with a refund while holding the counterpart payment. Hashlock vaults are always earmarked |
| R6 | Preimage length mismatch between chains | Either | A preimage valid on one chain and too long for the other. Both sides fix it at 32 bytes (`[H2]` and the counterpart requirement) |
| R7 | Hash function mismatch | Either | sha256 on both sides |
| R8 | A secret reused across trades | Seller | A counterparty of one trade learns the secret and claims the other vault without paying on the other chain; outputs still go to the named buyer, but that buyer has not paid. The contract cannot prevent it. `xchain new` and `xchain verify` refuse a hash_lock already seen in a known hashlock vault (`XCHAIN_HASH_REUSED`), the CLI makes a fresh secret per trade and never accepts one from outside, and the guarantee is documented as holding only with a fresh secret per trade |
| R9 | A Kaspa reorg removes the buyer's claim | Buyer | The claim stays valid and is rebroadcast (watcher); the seller can win the race only after expiry, so the buyer claims at least Δ before it |
| R10 | A counterpart reorg removes the seller's claim after the secret is public | Seller | The seller resubmits before T_C; the buyer can claim the asset meanwhile, which is the agreed outcome once the seller is paid. The seller relies on finalized commitment |
| R11 | Clock conversion between DAA score and the counterpart's clock | Buyer | The counterpart chain's clock can drift from wall-clock time (asserted, not measured here; I18 records the drift its counterpart source reports); the DAA rate varies around its target (modelled). Both must stay inside Δ and `DAA_RATE_MAX` |
| R12 | The buyer never locks (a free option) | Seller | The seller's asset stays locked until expiry_daa, since the vault is earmarked; the buyer can still send it home early. The seller grants the buyer a free option with no premium, bond or early abort. A known property, stated in the user guide and the risk statement (I18); the CLI recommends the shortest viable expiry (T_C plus Δ plus the funding window). The buyer can end the option early by sending the asset home (its counterparty refund); the seller cannot, because a seller refund before expiry is the race of R5. A seller early-abort, premium or buyer bond is D43, default not in v0.2 |
| R13 | The seller claims on the counterpart chain without checking the buyer's HTLC | Seller | The seller would reveal the secret for nothing while the buyer claims the asset. Step 5 is mandatory and the CLI's claim preparation runs it first |
| R14 | Front-running the Kaspa claim | none | The outputs are fixed by the script; a copy completes the same exchange |
| R15 | After expiry_daa the seller refunds the authorizer alone (`refund` with no token in the transaction; the token requires `[HR8]`, `[HR9]`, `[HR10]`, `[HR12]`, `[HR13]` and `[HR14]` run only when a token of the asset covenant is present, and `[HR11]` binds the buyer only), while the secret is already public on the counterpart chain and the buyer has not yet claimed | Buyer | The escrow stays owned by the vault's script hash and cannot move without an input at the vault's address, so the buyer's claim needs a new UTXO paid to that address, whose KAS then go to the seller (`[HS8]`, `[HS9]`); the token is not destroyed. The same new UTXO equally authorizes the seller's refund of the token, so after expiry the first accepted transaction wins, as in R4, and the seller can repeat the authorizer-only refund against each new UTXO. The claim-lead margin (Δ, section 10.5: the buyer claims at least Δ before expiry_daa) is the buyer's only protection; the script gives none after expiry. Pinned by `seller_authorizer_only_refund_after_expiry_leaves_a_race` (tests/engine/htlc_refund.rs; I18 review round 5) |

Generic sha256 chains follow the same flow and the same table with their own finality and clock; a chain whose HTLC cannot bound the claim falls under R3.

### 10.8 Core: `impulse_core::htlc` (I18 core step)

What the core step implements, following sections 10.2 to 10.5 and the defaults of D50, D51 and D52 where this file was silent. Nothing here changes the template or the design above.

- **Terms and hashes.** `HtlcTerms` is the field list of section 10.2; `Counterpart` the record. `encode`, `decode`, `terms_hash` and `Counterpart::hash` follow section 10.2 exactly. Decoding refuses, first failure returned: a version byte other than 1 (`HTLC_VERSION`, before anything else), input that ends inside a field (`TERMS_TRUNCATED`), a network, leg kind or owner type byte with no meaning (`TERMS_INVALID_TAG`), a counterpart chain byte other than `0x01` and `0x02` (`HTLC_COUNTERPART`), bytes after trade_ref (`TERMS_TRAILING_BYTES`). A KAS or external asset leg decodes in v1's Leg encoding and is refused by the structure checks (`HTLC_ASSET_KIND`).
- **Structure checks**, in the order of section 10.2. Two points where the section was terse: a PUBKEY owner must also be a valid x-only key (`TERMS_INVALID_KEY`), as v1 checks every KCC-20 destination; the counterpart record's identifiers, amount and timeout are checked in field order (chain_id, htlc_program, asset, amount, recipient, refund, timeout), each refusal `HTLC_COUNTERPART` naming the field (D51).
- **Creation checks.** v1's three, then the counterpart timeout strictly after `now_unix` (`HTLC_COUNTERPART`, field `counterpart.timeout`: a timeout already gone would pass the margin rule vacuously, so the core refuses it rather than leave it to callers), then `DAA_RATE_MAX`, then the margin. `DAA_RATE_MAX` is computed from a `DaaRateSample` (the node's blocks-per-second while sampling and `(unix seconds, virtual DAA score)` points, oldest first) as 1.5 times the highest rate over a fixed 10-minute window [t, t + 600] anywhere inside the sample, with the DAA score read linearly between the points around t and t + 600 (exact fractions; the maximum is at a window that starts or ends on a point, so those are the windows evaluated). A window from a point to the next point at least 10 minutes on is not used: with gaps of up to 10 minutes it can span nearly 20 and halve a 10-minute burst (review round 2). `HTLC_DAA_SAMPLE` refuses, in order: no sample on mainnet; fewer than two points; points not strictly increasing in time or with a falling DAA score; two consecutive points more than 10 minutes apart; a span under 7 days; another blocks-per-second than the pinned network's (`Params::bps()`, 10 for mainnet and TN10, asserted by a unit test); a last point after the time of the check; a last point more than 30 days before it; a mean rate, the DAA gained from the first point to the last over the time between them, below half the target rate (`Params::bps()` per second); no DAA progress in the busiest window. The result is raised to the target rate when 1.5 times the busiest window is below it. The shape refusals are this reading of "no DAA rate sample is given": a series that does not meet D45's definition is not a sample (D51). On testnet without a sample the rate is 2 times the target, 20 per second. The arithmetic is exact: the arrival of expiry_daa is now plus (expiry_daa minus the current DAA score) divided by `DAA_RATE_MAX`, rounded down; the D18 finality depth in seconds is 600 divided by `DAA_RATE_MAX`, rounded up (36,000 until I18 review round 5); Δ is that plus the counterpart's time to finalized commitment plus the retry window (default 1,800 seconds), and at least 3,600. The counterpart timeout T_C is read as unix seconds for both chain kinds (D51). Creation passes when the arrival is at or after T_C plus Δ. Sampling resolution (modelled, not measured): linear reading spreads a burst shorter than one gap over that gap. For a burst at rate B over a 10-minute window, base rate b elsewhere, and gaps of at most s seconds around it, the measured rate is at least ((600 minus 2s) times B plus 2s times b) divided by 600. At the sampling script's default of 60 s that is at least 0.8 B, so 1.5 times it covers B; at its maximum of 240 s it is 0.2 B plus 0.8 b, which 1.5 times does not cover for a burst above about 1.7 times the base. D67 records the interval choice.
- **Template.** The artifact and `TEMPLATE_HASH_HASHLOCK` are embedded and checked once, in v1's order (`HTLC_ARTIFACT_INVALID`, `HTLC_HASH_MISMATCH`), including the 18-field state layout of section 10.2. `HtlcVault::instantiate_existing` and `instantiate_for_creation` (the creation checks; only its result has a funding address) mirror v1's two vault kinds. `decode` returns the contract state (`HtlcState`: the terms with the counterpart record's hash): `HTLC_NOT_HASHLOCK_VAULT`, `HTLC_STATE_MALFORMED`, `HTLC_STATE_INVALID` (a network or owner type byte with no meaning, a negative integer, a template length above u32), the structure checks that do not need the record, then `HTLC_NONCANONICAL`. A unit test pins that the v1 decoder refuses a hashlock vault (`TEMPLATE_NOT_IMPULSE_VAULT`) and the hashlock decoder a v1 vault; an engine test pins that the core's vault is byte for byte the pinned compiler's output for the same state.
- **Builders** (`fund`, `claim`, `refund`), keyless, in the layouts of section 10.4, with v1's transaction rules restated (minimum KAS, the 100,000-gram cap per mass dimension, the relay fee, top-up of pass-through outputs where the contract checks "at least"). Refusal order: fund as v1's `fund_kcc20` (`TX_VAULT_MISMATCH`, `TX_EXPIRED`, `TX_TOKEN_TEMPLATE`, `TX_TOKEN_INPUT`, `TX_BELOW_MIN_KAS`); claim: the preimage (`HTLC_SECRET_LENGTH`, `HTLC_SECRET_MISMATCH`), `TX_TOKEN_TEMPLATE`, `TX_NOT_AT_VAULT`, `TX_ESCROW_MISMATCH`; refund: `TX_NOT_AT_VAULT`, `TX_REFUND_SIGNER` (the buyer without the token), `TX_TOKEN_TEMPLATE`, `TX_ESCROW_MISMATCH`, `TX_LEG_AMOUNT` (the buyer's token not exactly the amount); then v1's shared checks in v1's order. The claim is not refused after expiry_daa (R4). Compute budgets: v1's per-byte rule for a vault entry (17 script units per KCC-20 template byte plus 20,000, and 100,000 for the refund's signature check), with floors of 5 (claim) and 16 (refund) above the measured 3 and 13; the KCC-20 spends as v1. An engine test runs every builder's transaction at its committed budget for KCC-20 templates of 1,461, 3,771 and 6,081 bytes (measured).
- **The partially signed transaction** (`HtlcIpst`) holds the terms, the unsigned transaction, the spent UTXOs and one slot per input, with v1's `add_signature`, `finalize`, `assemble` and terms check (`verify_against_terms`, `IPST_TERMS_MISMATCH`). The claim's slot 0 carries the preimage in its signature script, as the contract needs it; it is public by then (section 10.5, step 6). Its JSON document form is not specified here and is the command line's step (D52).
- **Verifier.** `verify_address` (creation checks, then `VERIFY_ADDRESS_MISSING`, `VERIFY_ADDRESS_MALFORMED`, `VERIFY_ADDRESS_NETWORK`, `VERIFY_ADDRESS_MISMATCH`, reported for the asset leg), `verify_revealed_script` (`HTLC_NOT_HASHLOCK_VAULT`, the decode codes, `VERIFY_TERMS_MISMATCH` naming the state fields that differ, `counterpart` for the record's hash) and `verify_spent_input` (`VERIFY_NOTHING_REVEALED`, `VERIFY_INPUT_NOT_VAULT`, then the script), and `verify_funding` (section 10.5, step 3; review round 4): on a funding transaction the node accepted, its outputs only, the template is the terms' (`TX_TOKEN_TEMPLATE`), exactly one output pays the escrow's scriptPublicKey, the P2SH of the asset's template holding the vault-owned state of exactly the amount, not a minter, so a short or long amount, another owner, a minter or another template is no escrow, and it carries the asset's covenant ID, then at least one output pays the vault's address with no covenant (each `HTLC_FUNDING`); it returns both outpoints. It only reads, so it runs no creation checks and accepts mainnet terms. Whether the outputs are still unspent and final is the caller's check against its node. The v1 `VERIFY_` codes are reused where their meaning applies unchanged; no new `VERIFY_` code (D51).
- **Secret** (D50). `HashlockSecret` exists only with the non-default cargo feature `htlc-secret`: 32 bytes from the operating system's random source, sha256 as the hash lock, no `Display`, a redacted `Debug`, not `Clone`, zeroed on drop, its bytes reachable only through `expose` for the caller that writes the seller's file. The default build, which the WASM SDK and the watcher use, cannot make or hold one.
- **Vectors.** `tests/vectors/htlc/`, one JSON file per vector: `name`, `description`, `terms` (the field list of section 10.2, 64-bit values as decimal strings, owners as `{identifier_type, identifier}`, the counterpart record as an object whose `chain` is the lowercase name section 10.2 gives chain kind `0x01`, or `other_sha256` for `0x02`), `canonical`, `counterpart_record`, `counterpart_hash`, `htlc_terms_hash`, `template_hash` and `vault` (`redeem_script`, `script_hash`, `address`). Five vectors: both networks, both chain kinds, every owner type in both owner fields, the upper and lower bounds, and an expiry exactly on the margin. `scripts/vectors.sh` regenerates them and checks each again in Python from this section alone. Frozen once on `main`.

### 10.9 Command line: `impulse xchain` (I18 CLI step)

What the CLI step implements (`crates/impulse-cli/src/xchain.rs` with `xchain_doc.rs`, `xchain_counterpart.rs` and `xchain_tests.rs` beside it), following sections 10.5 to 10.7 and the defaults of D52 to D55 where this file was silent. It changes nothing above. Conventions are those of `spec/CLI.md`: testnet unless `--network mainnet`, nothing printed or written before every check of a command has passed, `CLI_*` codes where their meaning applies unchanged, and the hashlock refusals of section 8.5 with their own codes.

**Mainnet (D39 b, D40, D55; gate lifted 2026-10-15).** Every `xchain` command except `daa-sample` accepts `--network mainnet`. On mainnet each prints the race R2 disclosure on stderr before it does anything else, and the per-trade value cap applies as on any network (`CLI_VALUE_CAP_EXCEEDED` above it without `--i-accept-the-risk`). `XCHAIN_MAINNET_GATED` and `HTLC_MAINNET_GATED` are reserved and no longer returned.

**Files.**

- Hashlock terms file: a JSON object with exactly `terms` (the JSON form of the vectors of section 10.8), `canonical` (hex) and `htlc_terms_hash` (hex). A reader refuses it unless the encoding of `terms` equals `canonical` and its hash equals `htlc_terms_hash` (`CLI_TERMS_FILE_INCONSISTENT`); any other JSON is `CLI_TERMS_JSON`. A v1 terms reader refuses it (`CLI_TERMS_JSON`: unknown key), and this reader refuses a v1 terms file.
- Draft: the JSON form without `hash_lock`, with `nonce` optional (drawn from the operating system's random source when absent). A draft that carries `hash_lock` is `CLI_TERMS_JSON`: the hash lock comes only from the secret `xchain new` makes (section 10.5, step 1).
- Secret file: exactly 64 lowercase hex digits (the 32-byte secret, or the revealed preimage), optionally followed by one line feed. Written only as a new file with mode 0600; read only from a regular file that neither group nor others can access (Unix). Anything else is `XCHAIN_SECRET_FILE`, with a message that names the path and never the content.
- Known hash locks: a text file the user names with `--known-hashes`, one line per trade, `<hash_lock> <htlc_terms_hash>` in lowercase hex. It is this installation's record for `XCHAIN_HASH_REUSED` (section 10.6, R8): a hash lock listed with another terms hash is refused; the same pair again is the same trade. `xchain new` and `xchain verify` append their trade after every other check has passed, creating the file (mode 0600) if it does not exist. A line in another form is `CLI_FILE_READ`. A hash lock used in a vault this installation never saw is not found: no node index searches vaults by hash lock (D54).
- DAA rate sample: line 1 `impulse-daa-sample 1 <mainnet|testnet> bps <n>`, then one line `<unix seconds> <virtual DAA score>` per point, oldest first, as `xchain daa-sample` appends them. A file in another form, for another network, or larger than 4 MiB (read only up to the cap), is `HTLC_DAA_SAMPLE`; the points are then judged by `daa_rate_max` (section 10.8).
- The partially signed transaction of a hashlock trade (D52, D53): the document of `spec/IPST.md` with `"ipst": 3` and the hashlock terms' canonical bytes in `terms`. Every other key, the value forms, the signature script, the canonical rendering and the reading steps are those of `spec/IPST.md`, with step 2 reading "`ipst` is 3" (`IPST_UNSUPPORTED_VERSION` otherwise) and step 4 decoding hashlock terms (`HTLC_*`, `TERMS_*`). A v1 reader refuses it as `IPST_UNSUPPORTED_VERSION`, and this reader refuses a version 1 or 2 document the same way. The claim's input 0 carries the preimage in `script_before`, public on the counterpart chain by then (section 10.5, step 6); it is never printed. There is no combine: signers sign one copy in turn. The terms check is `HtlcIpst::verify_against_terms` (section 10.8).

**Counterpart source.** `--counterpart <url>` names the source of the counterpart chain, behind the `CounterpartSource` trait: the chain kind and chain ID, its clock, the lock that matches a counterpart record and hash lock, the claim of that lock with its preimage, and the submission of the seller's claim. Finality states are `seen`, `confirmed` and `finalized`; `finalized` is counterpart-final (section 4.8). This build has no source for any real chain (D27): any URL is `XCHAIN_CHAIN_UNSUPPORTED`, except `fake-counterpart://<path>` in builds with the test-only feature `offline-fake-node`, a JSON state file the tests and the scripts' self-test write. It is not a chain and proves nothing about one. A real source that submits the seller's claim needs a signature on the counterpart chain; it signs only through the CLI's signing module, and its design waits for D27 (D54).

**Node.** As `spec/CLI.md`, "Node". The node's blocks-per-second is read from the network ID its server info reports, through the pinned consensus parameters (mainnet and `testnet-10`): the pinned RPC has no blocks-per-second field (measured, source: rusty-kaspa a41a333, `rpc/core/src/model/message.rs`, `GetServerInfoResponse` and `GetBlockDagInfoResponse`). Another value, or a network ID with no pinned parameters, is `XCHAIN_NODE_BPS` (D54). Every `xchain` command that contacts a node checks this after the network and sync checks.

**Margin arguments.** `--counterpart-final-secs <s>` (the counterpart's time to finalized commitment as its source reports it; required where the creation checks run), `--retry-secs <s>` (default 1,800) and `--daa-sample <file>` (required on mainnet by `HTLC_DAA_SAMPLE`). Δ_claim is the larger of two hours and ten times `--counterpart-final-secs` (section 10.5). Now is the system clock, in unix seconds.

**Commands.** Each lists its checks in order; the first refusal is returned.

- `xchain new --draft <file> --my-key <hex> --my-counterpart-account <hex> [--my-refund <pin>] (--node <url> | --daa <score>) <margin arguments> --known-hashes <file> (--kas-equivalent <sompi> | --i-accept-the-risk) --secret-out <file> --out <file>`. The seller only (D32). The draft (`CLI_TERMS_JSON`); `--my-key` is `seller_key` (`CLI_ROLE_KEY_MISMATCH`); `seller_refund` pays `--my-key` as a KCC-20 PUBKEY owner or equals the `--my-refund` pin (`kcc20:<type>:<hex>`), and never pays `buyer_key` (`CLI_DESTINATION_NOT_MINE`, `CLI_DESTINATION_PIN_INVALID`); the counterpart record's `recipient` is `--my-counterpart-account` (`CLI_DESTINATION_NOT_MINE`). Then a fresh secret (D50) and its sha256 as `hash_lock`; the structure checks (`HTLC_*`, `TERMS_*`); the known hash locks (`XCHAIN_HASH_REUSED`); the node (or on testnet `--daa`; `CLI_MAINNET_NEEDS_NODE`) and its blocks-per-second; the creation checks with the margin (`TERMS_*`, `HTLC_DAA_SAMPLE`, `HTLC_TIMEOUT_MARGIN`); the counterpart timeout at least Δ_claim after now (`XCHAIN_MARGIN_TOO_SHORT`: the seller could not reveal in time); the pinned KCC-20 template (`CLI_TEMPLATE_UNPINNED`); the value cap of `spec/CLI.md` with the declared KAS equivalent; `--secret-out` and `--out` do not exist (`CLI_OUTPUT_EXISTS`). Then it appends the known hash lock, writes the secret file and the terms file, and prints the hashlock terms summary, the margin figures (`DAA_RATE_MAX`, the estimated arrival of expiry_daa, Δ, T_C plus Δ, and the latest reveal, T_C minus Δ_claim), the role check, the cap line, the vault address, `secret: written to <path> (mode 0600); not shown` and `wrote:`. The secret is never printed, logged or sent.
- `xchain verify --terms <file> --my-key <hex> --my-counterpart-account <hex> [--my-delivery <pin>] (--node <url> | --daa <score>) <margin arguments> --known-hashes <file> (--kas-equivalent <sompi> | --i-accept-the-risk)`. The buyer's check before locking on the counterpart chain (section 10.5, steps 3 and 4). The terms file and its network (`CLI_NETWORK_MISMATCH`); `--my-key` is `buyer_key`; `buyer_delivery` pays it or its pin and never `seller_key`; the record's `refund` is `--my-counterpart-account`; the known hash locks (`XCHAIN_HASH_REUSED`); the node and its blocks-per-second; the creation checks with the margin; the pinned template; the value cap. Then it records the trade in the known hash locks and prints the summary, the margin figures, the vault address and `ok:`. It does not check the funding: `xchain verify-funding` does, and the buyer locks only once it passes.
- `xchain verify-funding --terms <file> --node <url> --asset-template <file> --txid <hex> --from-block <hash>`. The buyer's check of the funding before locking (section 10.5, step 3). The node (transport, network, sync, blocks-per-second); the terms and network; the template (`CLI_TEMPLATE_MISSING`, `TX_TOKEN_TEMPLATE`); the transaction accepted on the selected chain from `--from-block` (`CLI_TX_NOT_ACCEPTED`), read with the UTXOs it spent (`get_virtual_chain_from_block_v2`); `htlc::verify_funding` (`HTLC_FUNDING`); the escrow and the authorizer it created still in the node's UTXO set as created (`CLI_UTXO_NOT_FOUND`); a depth of at least 600 DAA (D18, `XCHAIN_NOT_FINAL`). It prints the escrow and authorizer outpoints, the depth and `ok:`.
- `xchain fund build --terms <file> --node <url> --my-key <hex> <margin arguments> --pay-from <address> [--change <address>] [--fee <sompi>] --asset-template <file> --token <txid>:<index>:<amount>... [--carrier <sompi>] [--authorizer <sompi>] (--kas-equivalent <sompi> | --i-accept-the-risk) --out <file>`. The seller's funding (section 10.5, step 2), as `spec/CLI.md`, "fund build", for the asset leg: the terms and network; `--my-key` is `seller_key` (`CLI_FUND_NOT_YOUR_LEG`); the node; the creation checks with the margin; the template pin; the value cap; `--pay-from` the P2PK address of `--my-key` (`CLI_FUND_NOT_YOUR_LEG`); the template (`CLI_TEMPLATE_MISSING`, `TX_TOKEN_TEMPLATE`); each `--token` on the node (`CLI_UTXO_NOT_FOUND`); then `htlc::fund`, with the fee inputs of "Common arguments of the builders".
- `xchain verify-counterpart --terms <file> --counterpart <url> --counterpart-final-secs <s>`. The seller's mandatory check before revealing (section 10.5, step 5; R13). The source (`XCHAIN_CHAIN_UNSUPPORTED`); its chain kind and chain ID are the record's, and a lock is found whose program, asset, amount, recipient, refund, hash lock and timeout equal the record's and the terms' hash lock, and which is funded (`XCHAIN_COUNTERPART_MISMATCH`, naming the first field that differs); the lock is counterpart-final (`XCHAIN_NOT_FINAL`). It prints `ok:` and the latest time to reveal, T_C minus Δ_claim, on the source's clock.
- `xchain counterpart-claim --terms <file> --secret-file <file> --counterpart <url> --counterpart-final-secs <s>`. The seller's reveal. The secret file (`XCHAIN_SECRET_FILE`, `HTLC_SECRET_LENGTH`, `HTLC_SECRET_MISMATCH`); every check of `verify-counterpart` (R13 is not optional). If the source shows a claim of that lock revealing this preimage at counterpart-final, it prints `counterpart claim: counterpart-final` and is done. If it shows one that is not yet counterpart-final, it submits the claim again and reports `XCHAIN_NOT_FINAL`. If it shows none, the source's clock must be at least Δ_claim before T_C (`XCHAIN_MARGIN_TOO_SHORT`, R2; the first reveal only, since a resubmission reveals nothing new); it submits and reports `XCHAIN_NOT_FINAL`. The claim is reported done only at counterpart-final, never when submitted.
- `xchain watch --terms <file> --counterpart <url> --secret-out <file> [--polls <n>] [--interval-secs <s>]`. The buyer's reveal watch (section 10.5, step 6). `--secret-out` does not exist (`CLI_OUTPUT_EXISTS`); the source; a claim of the record's lock whose preimage passes the claim's preimage check (any other is ignored): none after the last poll is `XCHAIN_REVEAL_NOT_FOUND`, one not yet counterpart-final is `XCHAIN_NOT_FINAL`. At counterpart-final it writes the preimage as a secret file and prints the claim's identifier and `preimage: written to <path> (mode 0600); not shown`. - `xchain claim --terms <file> --node <url> --asset-template <file> (--secret-file <file> | --counterpart <url>) [--daa-sample <file>] [--retry-secs <s>] [--past-margin] --pay-from <address> [--change <address>] [--fee <sompi>] (--kas-equivalent <sompi> | --i-accept-the-risk) --out <file>`. ## 13. File ownership and change rules

The v0.2 increments were built as two parallel changes (I16 and I17; I18) that never edited the same lines. How their files were split between them was an internal build arrangement and is not part of the design.

Comparisons and published numbers (rule 7 of `docs/ENGINEERING-RULES.md`):

- The parity work compares design properties only, never performance or capability. No v0.2 text says or implies that Impulse is more capable, faster, cheaper or better than the baseline DvP program because v0.2 has features the baseline may lack; a feature is described for what it does, without a comparison.
- A `prose` entry of kind `none` on a line that holds a comparative word (more, less, better, worse, faster, slower, cheaper, only, unlike, beyond, superior) needs the owner's sign-off recorded under D41 before it merges; the default is that the line is reworded instead. `gen_parity.py` gains a check that fails on such an entry without a D41 reference in its `none` text.
- Practical N, script units and masses are published only from `docs/measurements/v2-max-n.txt` and the other committed measurement files, with method and raw data, and framed as limits of the pinned toolchain (section 9.3). Modelled figures of this file are never quoted outside it.

## 17. Linked trades: opening and return (I22, release v0.3)

Draft, 13 October 2026, increment I22. This section is self-contained and changes nothing above it: no template, no terms v2 field, no frozen vector. Decisions D102 to D106, each answered with its default.

### 17.1 What it is and what it is not

A linked trade is two ordinary two-leg v2 trades, an opening and a return, described by one term sheet. The opening moves asset A from party 0 to party 1 and asset B from party 1 to party 0. The return, later, moves an agreed amount of asset A from party 1 back to party 0 and an agreed amount of asset B from party 0 back to party 1. With asset A cash and asset B a security this is a repurchase agreement; with asset A a security and asset B cash collateral it is a securities loan. Impulse gives the mechanism, not the legal characterisation (D105).

- Each trade is an `ImpulseVaultV2` trade with the existing template and `TEMPLATE_HASH_V2`. Nothing is added to the contract. Each trade settles in one transaction or not at all, as any v2 trade does.
- The pair is not one transaction. The opening and the return are two settles with a gap between them, and the pair is not atomic. This section never uses that word for the pair (section 4.8 of this file governs wording: `accepted` and `final`, each per trade).
- If the return is never funded or never settles, each party keeps what the opening delivered to it. There is no margin, no mark to market, no price input, no liquidation and no default remedy. Whether what the opening delivered is worth the return is the parties' agreement, outside Impulse.
- Bilateral only: two parties, and each trade has exactly two legs. No partial settlement (`partial` absent in both trades).

### 17.2 The sheet (terms v2 extension `linked`)

The sheet is the one term sheet both parties agree. Its canonical bytes and hash are defined here; terms v2 itself (section 5) is unchanged and no frozen v2 vector changes. Conventions are section 5.2's: fixed-width little-endian unsigned integers, nothing after the last field.

| # | Field | Encoding | Bytes |
| --- | --- | --- | --- |
| 1 | link_version | u8, `0x01` | 1 |
| 2 | opening_len | u16 | 2 |
| 3 | opening | the canonical bytes of a terms v2 value (section 5.2) whose trade_ref is 32 zero bytes | opening_len |
| 4 | return_amount_0 | u64 | 8 |
| 5 | return_amount_1 | u64 | 8 |
| 6 | return_earliest_daa | u64 | 8 |
| 7 | return_expiry_daa | u64 | 8 |

```
linked_hash = BLAKE2b-256(key = "Impulse/terms/v2/linked", message = canonical sheet bytes)
```

Keyed BLAKE2b as section 5.1: 32-byte digest, the 23 ASCII bytes of the tag as the key, no padding, salt or personalisation. Known answers (measured with Python `hashlib`, as section 5.1): empty message `f0f21f6c2445993189163dbd26ee39bd3a600642664bc886d8e13c394eaf4e20`, `abc` `ce884529d5bc1a435dc5200c6f094b0d4ead1d747e57e478354b7260507b1241`.

Decoding is exact, first failure returned: a link_version other than 1 (`LINKED_VERSION`, before anything else); input that ends inside a field (`LINKED_TRUNCATED`); the opening bytes decode as terms v2 (the `TERMS_` codes of section 5.2, including a length that cuts or overruns the opening); bytes after return_expiry_daa (`LINKED_TRAILING_BYTES`). `decode(encode(s)) = s` and `encode(decode(b)) = b`.

The opening's own trade_ref is zero in the sheet because the sheet's hash is written into it on chain (17.3), and a hash cannot contain itself.

### 17.3 Deriving the two trades

`linked_hash` is computed from the sheet once. Both trades are then derived by pure functions of the sheet; no party supplies either trade separately.

Opening terms: the sheet's opening with trade_ref replaced by `linked_hash`. Everything else is as the parties wrote it: network, nonce, authority_key, legs, earliest_daa (optional), expiry_daa, funding_mode.

Return terms, leg i of 0 and 1 (j = 1 - i):

| Field | Value |
| --- | --- |
| version, network, nonce, authority_key, funding_mode | those of the opening. The nonce is shared: both trades carry it (no component keys anything by nonce; trades are named by terms hash) |
| legs[i].depositor_key | opening.legs[j].depositor_key (the party that received asset i at opening returns it) |
| legs[i].asset | the kind of opening.legs[i].asset (same token or KAS) with amount return_amount_i |
| legs[i].delivery | opening.legs[i].refund (asset i goes home to the party that deposited it at opening) |
| legs[i].refund | opening.legs[i].delivery (a failed return goes back to the party that funded it, at the address that party received asset i at) |
| earliest_daa | return_earliest_daa |
| expiry_daa | return_expiry_daa |
| partial | absent |
| trade_ref | `linked_hash` |

Leg order is kept, so the KCC-20 legs still come first (5.3). The two trades have different terms hashes (the depositors and the DAA bounds differ), so their vault addresses differ; each commits to `linked_hash` through trade_ref (4.2 field 12). A funded opening vault therefore belongs to exactly one sheet, hence one return schedule: changing any return field changes `linked_hash`, trade_ref and every opening address.

Hash names: `opening_terms_hash` and `return_terms_hash` are the terms v2 hashes (5.1) of the two derived trades; `linked_hash` is the sheet's.

### 17.4 Sheet checks

`ValidatedLinked` is obtained only by the sheet checks, in this order, first failure returned:

1. link_version is 1: `LINKED_VERSION`.
2. The opening passes the terms v2 structure checks (5.3): the `TERMS_` codes.
3. The opening has exactly two legs: `LINKED_LEG_COUNT`.
4. The opening has no partial: `LINKED_PARTIAL`.
5. The opening's trade_ref is zero: `LINKED_TRADE_REF_SET`.
6. return_earliest_daa is above the opening's expiry_daa: `LINKED_RETURN_NOT_LATER`.
7. The derived return terms pass the structure checks (5.3): the `TERMS_` codes (a zero or out-of-range return amount, a return bound that is not a DAA score, a return earliest above the return expiry, and the rest).

Creation checks (5.3, v1's) apply to each trade when it is created: the opening's at funding the opening, the return's at funding the return, each against the DAA score of that moment. The return's expiry horizon is therefore measured from the return's own creation, not from the opening's.

Why rule 6 is a strict comparison with the opening's expiry and not its earliest: the Impulse builders and an honest authority refuse a v2 settle at or after expiry_daa (`TX_EXPIRED`, 4.4), so under that policy the opening has settled, or will not be settled by them, before the return can start. The return's settle lock time (its earliest) is then past the opening's fate. This is a builder and authority rule, not an on-chain one: as in v1 (`IMPULSE-SPEC.md` red team, "Settle after expiry cannot be forbidden in script"), the vault script does not forbid a settle at or after expiry_daa, so a hand-built settle signed by the parties or the authority can still settle the opening late, after the return has started (17.12, row 13). This is the only ordering the sheet can state without a new contract.

### 17.5 Verifying terms against the sheet

`verify_terms(sheet, role, terms)` compares the offered terms' canonical bytes with the derived trade of `role` (`opening` or `return`). In order: equal, accepted; equal to the other role's derived trade, `LINKED_ROLE_MISMATCH`; equal to the derived trade of `role` in every field but trade_ref, `LINKED_TRADE_REF`; anything else, `LINKED_NOT_A_LEG`. The CLI runs it before it builds anything from a terms file that names a sheet.

### 17.6 Builders, the return gate and evidence

Both legs use the section 6 builders on the derived terms; the core module `impulse_core::linked` wraps them by role (`fund_kas`, `fund_kcc20`, `settle`, `refund`) so that a caller names a sheet and a role and cannot pass terms of another trade. The wrappers add one rule (D103).

- Opening builders (fund, settle, refund) and the return refund need nothing more.
- Return fund and return settle need an `OpeningSettled` value for this sheet. It is made only by `check_opening_settled(sheet, tx, spent)`, which is `check_settled(sheet, opening, tx, spent)` keeping the sheet's hash: `tx` is a transaction whose input 0 and input 1 each reveal the vault script of leg 0 and leg 1 of the trade (`verify_spent_input`, section 7, against the scriptPublicKey of the UTXO the input spent, `spent[i]`), and each of those inputs calls the `settle` entry of the pinned v2 artifact (the dispatch tag is the second-to-last push of the signature script, and is read from the same artifact file the v2 module embeds). Anything else is `LINKED_SETTLE_EVIDENCE`. A return builder given no value, or a value for another sheet, refuses with `LINKED_OPENING_NOT_SETTLED`.
- `check_settled` takes the role, so the same reading serves the return's own settle (receipts, 17.8).
- What core cannot check: that `tx` was accepted by the chain, how deep, and that it was not reorganised away. Those are the caller's: the CLI reads them from the node each time it builds a return fund or settle, and takes a minimum depth the user names, with no default (17.9). The core check is that the transaction is a settle of these vaults; the contract has already run its requires if the chain accepted it.

The gate guards honest mistakes. It is not a contract rule: a party who builds a return trade without these builders can fund its vaults. The contract cannot know the opening's fate. Section 17.12 rates this.

### 17.7 Refund and failure outcomes

Each vault has the v2 refund entry (4.5), unchanged; either trade's refund needs only that trade's terms.

| Case | Outcome |
| --- | --- |
| An opening leg is never funded | Funded legs are refunded to their refund destinations (revocable funding at any time, earmarked after expiry), as any v2 trade (4.7). No return is built: `check_opening_settled` has nothing to check. |
| Opening settles, return legs funded, return settles | Each party holds what it started with, with the agreed amounts (the fee is the difference between return and opening amounts). |
| Opening settles, a return leg is never funded | The funded return leg is refunded to its refund destination after the return's expiry (or at any time if revocable). Each party keeps what the opening delivered (17.1). |
| Opening settles, return funded by both, return never settled | As above: both return legs are refunded home; each party keeps what the opening delivered. |
| Opening refunded, return funded anyway | Prevented by the gate (17.6); if built outside it, the return would settle on its own terms and the parties would exchange assets in reverse with no opening. The watcher flags a return funded before the opening settled (17.9). |

### 17.8 Linked receipt

One receipt per leg trade, signed by whoever observed the settle, in the form of the version 1 receipt (CLI.md, "Settlement receipt") with the sheet added (D104). The version 1 and version 2 receipts are not touched.

Canonical bytes, 147 bytes: version u8 (`0x01`), network u8 (0 mainnet, 1 testnet), role u8 (0 opening, 1 return), linked_hash 32, leg_terms_hash 32 (the terms v2 hash of the settled leg trade), txid 32, accepting_block 32, daa_score u64, depth u64 (little-endian). Digest `BLAKE2b-256(key = "Impulse/receipt/linked/v1", message = canonical bytes)`, the 25 ASCII bytes of the tag as the key. The signer is not in the digest. JSON keys, in order: `version`, `network`, `role` (`opening` or `return`), `linked_hash`, `leg_terms_hash`, `txid`, `accepting_block`, `daa_score` (decimal string), `depth` (decimal string), `signer`, `signature`.

Verification against a sheet: the signature (`RECEIPT_SIGNATURE_INVALID`), the network equals the sheet's, `linked_hash` equals the sheet's hash and `leg_terms_hash` equals the sheet's derived hash for the receipt's role (`LINKED_RECEIPT_TERMS`). A pair (an opening receipt and a return receipt) is accepted only if both name the same `linked_hash`, the same network, roles opening then return, distinct txids, and the return receipt's daa_score is above the opening receipt's (`LINKED_RECEIPT_PAIR`). So both receipts link to one terms hash, `linked_hash`, and each ties to its own trade's hash through the sheet.

What a receipt does and does not establish. `linked receipt sign` refuses to sign unless the transaction the node accepted is a settle of the role's two vaults (`check_settled`, 17.6, against the scriptPublicKeys the node reports the inputs spent), so a signed receipt binds its transaction to the trade, which a version 1 receipt does not. A reader without a node cannot check that: to them the receipt is the signer's assertion that a transaction was accepted at a block, and `impulse decode` or `linked receipt verify --node` is how they check the chain facts. The pair check says nothing about whether the return was complete or whether the amounts were right beyond the sheet.

### 17.9 Command line and watcher

Command line, `impulse linked` (spec/CLI.md is updated with the full list):

- `linked new --draft <file> --return-amount-0 <n> --return-amount-1 <n> --return-earliest-daa <n> --return-expiry-daa <n> --out <sheet file> [--node <url> | --daa <n>]`: takes an opening draft (terms v2 JSON with `trade_ref` all zero; `nonce`, `expiry_daa` and `funding_mode` may be null and are filled as `v2 terms new` fills them), runs the sheet checks and the opening's creation checks, and writes the sheet file (`sheet` JSON view, `canonical`, `linked_hash`).
- `linked show --sheet <file>`: both trades, role by role, with who deposits what, amounts, DAA bounds, fee per asset, and the 17.1 exposure sentences.
- `linked terms --sheet <file> --role opening|return --out <terms file>`: writes the derived terms v2 file for that role (the file `v2 address`, `v2 verify`, `v2 ipst sign`, `v2 status` and the watcher read).
- `linked check --sheet <file> --role <role> --terms <file>`: 17.5.
- `linked return-gate --sheet <file> --node <url> --opening-txid <txid> --opening-from-block <hash> --min-depth <DAA>`: finds the transaction on the node's virtual chain as `v2 status` does, requires its accepting block to be a chain block at a depth of at least `--min-depth` (`CLI_TX_NOT_ACCEPTED`, `CLI_DEPTH_BELOW_MINIMUM`), runs `check_opening_settled` against the scriptPublicKeys the node reports the inputs spent, and prints the transaction, block, DAA score and depth. It reads only.
- `linked fund build`, `linked settle build` and `linked refund build` take `--sheet <file> --role opening|return` before the arguments of `v2 fund build`, `v2 settle build` and `v2 refund build`, run `linked check` on the `--terms` file for the role (`LINKED_ROLE_MISMATCH`, `LINKED_TRADE_REF`, `LINKED_NOT_A_LEG`), and then run that `v2` builder unchanged. For the return, fund and settle also take `--opening-txid`, `--opening-from-block` and `--min-depth` and run the return gate against the node first (`LINKED_OPENING_NOT_SETTLED` if any of the three is missing, `LINKED_SETTLE_EVIDENCE` if the transaction is not the opening's settle); the refund takes none. They print the sheet's hash, the role, the gate result and the 17.1 exposure sentences, then the `v2` builder's output, and nothing at all if either part refuses.
- `linked receipt sign --sheet <file> --role <role> --node <url> --txid <txid> --from-block <hash> --min-depth <DAA> --key-file <file> --out <file>`: finds the settle on the node, requires depth, runs `check_settled` for the role (`LINKED_SETTLE_EVIDENCE`), and signs the linked receipt through the signing module.
- `linked receipt verify --receipt <file> --sheet <file> [--signer <hex>] [--txid <txid>] [--node <url>]` and `linked receipt pair --opening <file> --return <file> --sheet <file> [--signer <hex>]`: 17.8.

Watcher: `impulse-watch run --linked <sheet file>` (repeatable; the sheet file is read as a terms file is: `WATCH_TERMS_FILE_INVALID`, `WATCH_TERMS_FILE_INCONSISTENT`) adds both derived trades as ordinary watched trades (their events are unchanged) and tracks the link. After each poll it reports one `linked` event when the link's phase changes, naming `linked_hash`, both trade ids, the phase and the txid that moved it. Phases: `opening_open`, `opening_settled`, `opening_refunded` (any opening leg refunded and not both settled), `return_settled`, `return_refunded`. A return vault funded (exactly the leg amount, `exact`) while the opening is not settled carries the flag `WATCH_LINK_RETURN_EARLY`. Phases come from the acceptances the watcher currently holds, so a reorg that removes the opening settle moves the phase back. An acceptance that reached the finality depth is remembered even after `--retention-daa` evicts it, so eviction never moves a phase back; a reorg of an acceptance already reported final (`WATCH_FINAL_REORGED`) does not either. The state file is unchanged: on a restart the phase is recomputed from the acceptances the file holds, and a link event is reported only for a change after it. The `linked` event is reported in the poll that caused the change, after that poll's other events; its `txid` is that of the last event of the poll that touched either trade. Its de-duplication key is `round`, `event`, `linked`, `phase` and `txid`.
